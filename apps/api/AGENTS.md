# API Agent Notes

## Scope And Architecture

- These instructions apply to `apps/api`. Root workflow and deploy rules still apply.
- The NestJS/Fastify API uses Prisma/Postgres and BullMQ/Redis. Runtime processes share one image and split work with `APP_ROLE`; `APP_SERVICE_NAME` selects the typed queue/service profile in `src/runtime/runtime-topology.ts`.
- Keep the runtime topology aligned with both production Compose files and `infra/scripts/lib/deploy-topology.sh`.
- Ingress accepts public health/webhooks, admin serves `/api/v1/` and local owner APIs, enqueue materializes queue work, moderation roles process their assigned queues, and action dispatches MAX actions.
- `api-media-analysis` owns OCR admission, source download, and policy; production native Sharp/Tesseract work runs only in the no-network/no-secret `ocr-native-sandbox` over bounded UDS IPC. Keep both single-concurrency and resource-capped, verify normal Tesseract process-group teardown, recycle the whole sandbox after forced native timeouts or abandoned in-flight native work, and keep the exact live sandbox-backed native identity bound to every commercial deletion. Commercial OCR `baseline` is the strict delete-only product policy under each chat’s `commercialAdsFilterEnabled` opt-in; `canary`/`on` expansion retains independent corpus/certification gates and fresh exact-chat Redis control. Never represent baseline as a certification or fabricate a control revision/expiry.
- Exact duplicate-photo native decoding runs in the independent `photo-native-sandbox` over `/run/maxim-photo/native-photo.sock`; only `api-moderation-background` mounts its IPC volume. Keep its own one-worker capacity, no-network/no-secret environment, and kill/reap-before-release lifecycle. Forced timeout or abandoned native work recycles the whole sandbox. Photo proof checkpoints include byte/pixel costs and charge cached members to the resumed album budget; partial albums never authorize matches. The raster hash/version remains independent of the checkpoint envelope.
- OCR heavy stages use the governor's recovery-window option only with its fresh queue/host checks. Active MAX/mixed degradation, manual pause, queue pressure and native limits still apply; recovery never renews a job deadline or authorizes a delete. Image-owned native manifests and probe expectations require exact `0444` permissions regardless of the build umask.
- Image stop-list OCR is a separate explicit per-chat, delete-only policy. Require two high-confidence word-span passes, keep OCR text out of jobs/DB/logs, persist its strict binding under the rollback-safe `COMMERCIAL_OCR_DELETE` sentinel, and re-check runtime, settings, active domain allowlist, author access/immunity, exact photo identity, native behavior, and the absolute deadline before every delete dispatch.
- Runtime hot paths must go through `WebhookIngestionService`, `ModerationExecutionService`, `MaxActionDispatchService`, and `ManagedEntitiesDiscoveryService`, not legacy implementations.
- `WebhookLegacyHoldService` is a mandatory Prisma-only production reader for installed legacy dispositions. Permanent message/member/global-user/exact-child holds deny new effects before local state/immunity mutation and at final MAX boundaries; exact confirmed receipts may settle SQL first. Only sealed v1 dispositions release ordering. The reviewed host cold controller installs finite permanent holds only with all 14 API roles and both native auxiliaries stopped; independent positive SQL readback and held receipt materialization precede restart. Runtime consumers cannot create or expire holds. Fresh post-seal admin commands use the persisted command-only path and current actor/bot authorization; they never waive automatic holds. Both rollback paths require these readers. See `docs/operations/runbooks/legacy-webhook-order-recovery.md`.
- Modern started-owner recovery uses `MODERN_SOURCE_ABANDONMENT_V1` with explicit `HUMAN_CHAT_V1` and `CHANNEL_AUTHORLESS_V1` source profiles. The human profile requires the original human sender; the channel profile proves author absence and persists a real null author. Strict direct media, finite flat forwards/replies, bounded formatting and passive channel buttons must match the real parser and reject default/configured commands. Only the original recipient/message/author supplies identity; linked identities never supply held targets. Legacy recovery keeps its unchanged profile. Modern recovery holds the exact source message family and attributed children, including exact channel-auto-post markers; it never creates member/global-user immunity or rewrites unknown action journals. Source owners, started claims and positive receipt proofs remain retained. Only sealed positive receipt projection releases ordering; independent unfinished edited claims remain refused. See `docs/operations/runbooks/webhook-source-abandonment.md` for the finite content matrix and cold protocol.
- Runtime signal handling goes through `runtime/runtime-worker-shutdown.ts`: pause and bounded-drain BullMQ workers while Prisma/Redis clients are still alive, then close the Nest context under the hard deadline. Do not restore direct `enableShutdownHooks()` calls in `main.ts`.
- Name-only Bull queues use `runtime/runtime-queues.ts` so Nest reuses registration metadata inside one context. Custom prefixes/connections/retry policies stay outside this registry; never cache live Queue/client instances across contexts or replace worker blocking connections with fail-fast producer clients.
- Shared governors, readiness, metrics and watchdog belong to `SystemRuntimeModule`; `SystemModule` adds the HTTP/dashboard facade and reexports it. Explicit `message-retention` startup uses `MessageRetentionAppModule` without HTTP/Auth/Admin imports, retaining all delete guards and runtime governors. Validate composition with `runtime-role-graph.spec.ts` and `runtime-retention-graph.spec.ts`.
- MAX API observational counters have compatible legacy/minute readers. Validated runtime configuration defaults to `MAX_API_METRICS_STORAGE_LAYOUT=minute` only after the compatibility release; activation requires all shared-image roles to have compatible readers and both rollback paths to enforce that reader source floor. Explicit `legacy` downgrades writers without relaxing the floor. Service counters retain their original 120-second last-write expiry. Do not change authoritative GCRA keys/TTL or dual-write an event. See `docs/operations/runbooks/memory-optimization-rollout.md`.
- Admin entry points should use `ManagedEntitiesService`, `AdminSettingsService`, `ManagedBroadcastService`, `ManualModerationService`, `ChannelDialogService`, and `ManagedGiveawayService` instead of growing legacy `AdminService`.
- Refactor guards track real `*.legacy` files. New code imports public facades; only thin facade modules may import legacy implementations.
- Ingress `SystemModeService` polling and readiness use `QueueMetricsService.getLagSnapshot()`: retain raw oldest `RECEIVED`/`QUEUED` age and use operational lag for fleet pressure. Only an exact enforced, unstarted `PENDING` execution wait may contribute lateness from the earlier of its scheduled retry and immutable deadline instead of receipt age; expiry lateness keeps growing even if retries advance. Its conditional proof materializes at most 65 indexed receipt heads, projects scalar proof only, and retains the last head at raw age; missing/malformed/fenced proof fails closed. Runtime governors use `getOperationalSnapshot()`, which adds fixed BullMQ default-shard/action counters and bounded dynamic-lease summary. Per-bot, unbounded JSON, count, action-health, auxiliary-queue and dynamic full-fleet fanout belong only to the closed dashboard snapshot; health may read cached detail but never refresh it.

- A slow, failed, retrying or quarantined event must not starve unrelated chats, administrator commands or queue shards. Keep SQL/Redis work and ordering waits bounded within the dependent scope, preserve independent admission capacity, and never throttle or stop the whole fleet solely because of oldest queue age. Verify independent progress with a blocked head and backlog.
- Dependency quarantine parks positively unstarted ordered successors behind pending timeouts as `QUARANTINED`; ordinary terminal FAILED owners isolate only their pristine semantic copies, preserving progress of other messages in the same chat. Preserve the exact failed predecessor and all effect evidence. Keep claim-before-receipt locking, final READY/start status and saved-deadline checks, bounded due reconciliation and retention pins. The journal is keyed by receipt plus blocker so repeated incidents retain separate attribution. Only exact clean predecessor/COMPLETED-claim proof permits a return to ordinary admission; expiry retains quarantine without business replay. Raw active lag and bounded quarantine count/age remain separate. Run native `webhook-dependency-quarantine-postgres.spec.ts`; see [the runbook](../../docs/operations/runbooks/webhook-dependency-quarantine.md).
- Lightweight oldest-pending metrics use `buildOldestPendingWebhookQuery`: literal RECEIVED/QUEUED status, covered `(status, created_at, id)` head selection, then one primary-key metadata read. Preserve the full order and native retained-history/empty-queue plan checks in `webhook-operational-lag-postgres.spec.ts`.
- Outbox polls serialize selection while carrying bounded in-flight work across polls. SQL scan cursors may advance only over representatives retained through final selection and eventual dispatch; keep pending identities bounded and re-read current eligibility before admission. An unfinished operation retains its concurrency slot and same-chat/event exclusion until its actual completion; polling deadlines must neither cancel it nor release its authority. Drain owned work through runtime shutdown before closing stores. Keep the native fleet-admission regression for a slow operation and a fresh independent chat.
- Permanent holds on uncertain automatic effects must permit exact fresh persisted administrator commands under current bot/actor authorization and command authority. Never replay an uncertain original, fabricate completion, or relax automatic-effect holds to unblock a command.
- Legacy receipt claim lookup uses `readLegacyReceiptClaims`: exact event probes and at most 32 indexed kind-prefix probes preserve unknown-kind semantic aliases. `semantic_key` alone has no leading index; never restore the unqualified semantic `OR` scan over retained claims.
- Legacy source classification allows at most 1,000 ms of MAX clock lead over receipt/current time, without changing cutover, raw timestamps or execution deadlines. Existing `LEGACY_EXECUTION_UNVERIFIED` holds remain installed. Pristine nonordered `user_removed` and `message_removed` mirrors inherit that exact hold under claim-before-receipt locks; they never remain an endlessly deferred active backlog or acquire execution/completion authority. Run the native removal-mirror and outbox regressions when changing this boundary.

## Validation And Prisma

- Queue/notice changes must follow the [latency prevention regression matrix](../../docs/operations/runbooks/webhook-latency-prevention.md). Receipt/payload-only hot-path updates retain single-statement CAS/status and JSON no-op guards; multi-step invariants retain transactions. SQL page limits must precede expensive eligibility probes and preserve the raw cursor; verify retained-history/skew plans with real stores.
- A persisted subscription notice/album handoff may finish without dispatch only for the exact typed rejection from its own final `beforeSend` callback. Source GET 404 is not deletion proof; retain persisted feature/violation evidence and write no delivered coverage. Source 503, member GET 404, lease loss, attempted/ambiguous sends and post-authorization errors remain fenced. Run both `required-subscription-notice-recovery.spec.ts` and native `webhook-multibot-moderation-guards-fullpath.spec.ts`; require next same-chat progress and no started-handler replay.
- A direct channel decoration may hand off a genuine first-PUT executor-proof rejection only after an exact live-marker CAS retains `IN_PROGRESS`/`edit_message` for guarded background recovery. It proves neither delivery nor historical handler completion. Forwards, quick buttons, lost leases, failed persistence and uncertain mutations remain fenced; run channel-button/marker tests and native moderation-guards full-path coverage for same-channel progress and fresh access/source-hold refusal.
- Required-subscription source-author GET 429 or a concrete `MaxApiInternalRateLimitError` at the exact author/source read may defer only through the existing initial no-effect or persisted SEND/DELETE handoff boundaries. Require explicit GET provenance for HTTP 429; local pre-dispatch failures must have no HTTP response or conflicting method. Preserve attempted/ambiguous effects; final dispatch rechecks fresh author rights. An omitted immediate DELETE schedule with an elapsed explicit deadline creates `EXPIRED` without renewal and preserves any conflicting existing intent, schedule, retention ownership and reasons unchanged; explicitly inverted schedules still fail.

- Explicit bulk abandonment uses permanent `CANCELLED` receipts and exact semantic/message/child tombstones, preserving uncertain claims. Only the stopped-fleet host writer creates an operation; runtime may project late copies after its seal. Never reset cancelled receipts or treat them as successful executions. See `docs/operations/runbooks/webhook-backlog-cancellation.md`.

- Focused validation: `npm run check:api`, `npm run check:prisma`, or `npm test --workspace @maxim/api -- -- -- --testPathPatterns='src/admin/publication-.*spec.ts$'` while iterating. Anchor patterns to `src/`: Jest matches absolute paths, including the worktree name.
- Public API build/typecheck/test scripts serialize codegen through repo file locks. Do not invoke `*:unlocked`, `*:source`, raw Prisma Generate, and another API validation concurrently.
- Run disposable PostgreSQL race checks with `TZ=UTC`: raw `pg` interprets `timestamp without time zone` in the process timezone, while Prisma reads the stored UTC value. Local non-UTC runs otherwise produce false lifecycle/epoch mismatches.
- The disposable PostgreSQL server/session must also report `TimeZone=UTC`. A non-UTC server converts `CURRENT_TIMESTAMP` into local wall time for timestamp-without-time-zone lease/default columns even when the test process has `TZ=UTC`, causing false pending-lease failures.
- Without Docker, `node scripts/agent/with-test-stores.mjs --migrate -- npm run test:postgres-races --workspace @maxim/api` creates and removes its own local PostgreSQL/Redis. SQL hot-path changes need real-store fixtures with representative history/skew and bounded EXPLAIN row/probe work; `LIMIT` and small mocks alone do not bound scans, sorts or correlated subplans. Keep due retries separate from retained-history recovery budgets.
- The built entrypoint is `dist/apps/api/src/main.js`; `npm run build --workspace @maxim/api` cleans output and checks that stale modules are absent.
- Prisma 7 uses `apps/api/prisma.config.ts` from repo root or `prisma.config.ts` from this workspace. Dependency security anchors hoist the pinned CLI, so in API containers call `./node_modules/.bin/prisma` from repo root.
- Runtime code imports Prisma through `src/prisma/prisma-client.ts`, not `@prisma/client`; generated client output is ignored under `src/generated/prisma/`.
- Model, enum, or database mapping changes in `prisma/schema.prisma` require a migration; generator/datasource-only changes do not.
- `config/prisma-migration-policy.json` pins names and content digests through the latest committed migration. A new migration must advance that immutable baseline in the same reviewed change; `policyRulesAfter` is the fixed bootstrap cutoff and must never advance. Never edit or delete historical `migration.sql` files.
- Destructive column removal requires two runtime releases: first ship a client/schema that no longer selects the columns while DB columns remain, then drop them only after every API role runs the compatible client.
- Statistics participant names use `chat_user_display_names` before temporary local history. `allowRemoteLookup: false` disables MAX calls, not local resolution. Backfill only with bounded `npm run stats:backfill-display-names -- ...` runs.
- Raw `webhook_events` display-name fallback must keep the shared event-type allowlist and the exact predicate used by `webhook_events_local_display_name_chat_user_created_idx`; broad JSON scans are not an acceptable fallback.
- Message-retention cancellation releases active credit once and keeps ambiguous/remote-success receipts separately scheduled. Recovery never dispatches DELETE; mode off permits database-only success settlement. Safety Desk retry must atomically check current activation, intent versions, evidence and quota, then schedule the normal guarded worker.
- Run `test:retention-storage` with explicit localhost `MAXIM_TEST_POSTGRES_URL` and `MAXIM_TEST_REDIS_URL` for real store races and BullMQ slot/concurrency recovery. The same public wrapper owns codegen; no live MAX calls are needed.
- Retention cleanup runs sequentially in bounded ordered batches and does not run at process startup. Keep a shared total budget for status groups that previously cleaned together.

## MAX Transport

- Major and Publisher activation is exact-bot and administrator-initiated. Confirmed denial/removal or known missing baseline capabilities remain dormant beyond TTL; passive lifecycle, cache refresh and owner promotion cannot restore them. Genuinely new bindings carry their profile's pending-activation source until an authenticated fresh `Старт` or exact-bot private forward proves explicit human and bot admin/owner privileges. Existing transient/unknown refresh evidence is not a new pending connection. Major requires chat read-all plus write-based deletion, or channel deletion plus exact channel GET; Publisher uses its own publication rights. Retained Major purpose ceilings cannot gain known-absent optional rights passively. Dormant ordinary receipts without an already proven healthy peer or owned claim settle only their exact observation marker; never touch shared execution authority or replay them after activation. Both rollback paths must preserve these readers.

- Verify MAX Bot API, Mini Apps, `init_data`, webhooks, and deep links against current docs, in this order:
  1. `https://dev.max.ru/docs/`
  2. `https://dev.max.ru/docs-api/`
  3. `https://help.max.ru/help/bots`
  4. `https://github.com/max-messenger`
- MAX removed bot-wide `GET /chats`; keep `listBotChats` compatibility out of production discovery and never build a new flow on it.
- Send bot tokens only as `Authorization: <token>`, never query parameters. Keep tokens and webhook secrets only in ignored env/VPS secrets.
- Production delivery uses webhooks. Long polling is development-only and cannot coexist with a webhook subscription.
- The MAX overview documents a 30 rps ceiling without defining its scope across unrelated tokens. This project enforces 30 rps independently per bot token and has no additional aggregate 30 rps hard guard; use existing per-bot queues, lane/source tags, route priorities, and per-role class limits rather than direct hot-path calls.
- The runtime image carries the Russian Trusted Root/Sub CA bundle under `infra/certs/` via `NODE_EXTRA_CA_CERTS`; preserve it in API Docker changes.
- MAX permissions are entity-sensitive: group-chat `write` permits message deletion and channel posting, but channel edit/delete requires `edit`/`edit_message` and `delete`/`delete_message` respectively.
- In hot paths prefer targeted `getCurrentChatMemberAccess` or `getChatMembersAccess`; fetch a full admin roster only when the feature needs it.
- For `GET /chats/{chatId}/members`, send multiple IDs as one comma-separated `user_ids` value; repeated parameters can collapse to the first user.

## Webhooks And Deletion Safety

- `POST /subscriptions` is transport source of truth: public HTTPS on port 443, trusted full-chain TLS, HTTP 200 within 30 seconds, and `X-Max-Bot-Api-Secret` validation when configured.
- Keep required subscriptions aligned with `src/max/max-webhook-subscription.constants.ts`: the base set is `message_created`, `message_edited`, `message_callback`, `user_added`, `user_removed`, `bot_added`, `bot_removed`, `bot_started`, `chat_title_changed`, and `bot_admin_permissions_changed`. Shadow/canary/on also subscribe to `message_removed`, `bot_stopped`, and `dialog_removed`; shadow records those events without applying terminal lifecycle transitions, while off omits them.
- `MAX_REQUIRED_WEBHOOK_UPDATE_TYPES` is the product subset of official updates. Add parser, queue, and product handling before subscribing to additional lifecycle events.
- After changing a webhook host/domain, read `GET /subscriptions` and recreate the target; do not assume its secret binding changed automatically.
- Keep `APP_BASE_URL` and `MAX_WEBHOOK_BASE_URL` aligned with the canonical host, currently `https://major-maksimov.ru`.
- Webhook `dedupKey` is bot-scoped (`botId:updateId`). Dedupe logical side effects later by message/update semantics.
- Publisher receipt completion is observation-only: keep its `publisher-observation:v1` semantic namespace separate from moderation EXECUTION authority. A PROCESSED Publisher observation must never suppress or block moderation of the same event; historical shared keys require reviewed recovery, not weaker prior-effect guards.
- Retryable canonical preparation failures before the business handler use the same locked BullMQ job with the original retry delay. Mark this path only around `prepareExecution`; never treat handler/completion failures as ordinary preparation retries, renew source deadlines, or clear prior-effect fences.
- Stateful moderation always uses one semantic EXECUTION authority (`semantic-owner-lease-v1`), including diagnostics modes off/shadow. Immutable readiness deadlines derive from the original receipt/source (5 minutes text, callbacks, user joins and chat title changes, 10 minutes strict IMAGE); callbacks use the receipt time rather than an old button message. Previously waiting work cannot revive after expiry. A started whole-engine attempt never reruns: independently fenced action/delete/media journals own continuation, and only exact completion evidence permits SQL settlement. Saved command notices may switch only a certified unattempted SEND under the original deadline and both leases; unknown sends remain fenced. Completed semantic claims survive body retention as tombstones; every historical unenforced unfinished claim requires exact effects proof before recovery.
- Use `Update.timestamp` as event/edit time; `Message.timestamp` is creation time and cannot identify successive edits.
- Unfinished enforced EXECUTION claims created before the successful multibot authority migration also require exact effects proof: the previous runtime could release a lease after partial effects without a business-start marker. Check saved readiness deadlines and live leases with the database clock at the final preparation/start transition.
- Moderation enforcement and retry-critical cleanup use durable `ModerationDeleteIntentService` intents. Direct delete belongs only inside intent execution or explicit shadow/off compatibility.
- `MODERATION_DELETE_CROSS_BOT_CANARY_CHAT_IDS` is an execution-time kill switch and must affect already stored intents.
- Replacement-message cleanup has a separate execution-time switch, `MODERATION_DELETE_INTENT_REPLACEMENT_CLEANUP_ENABLED`, limited to the exact rule-code allowlist in `ModerationDeleteIntentService`. Preserve requested routing while the switch is off, promote legacy `origin_only` rows during recovery, and allow survivor routing only for user-authored chat replacements; channel and bot-authored cleanup stays origin-only.
- Keep replacement-message cleanup disabled by default. Enable it only after a bounded capability/backlog audit confirms that critical-lane capacity can absorb the existing intents.
- A delete succeeds only on documented `{ success: true }` or message-specific absence confirmation. An arbitrary HTTP 404 is not proof that a message is gone.
- Native voice deletion uses the authenticated `moderation_voice_sources` proof when MAX GET omits the message. Capture and edit/removal revocation commit with ingress receipts; only new bound `VOICE_BLOCKED_DELETE`, `MUTE_ACTIVE_DELETE`, `NIGHT_MODE_DELETE` and `MANUAL_GROUP_CLOSE_DELETE` reasons may use the original five-minute deadline. State reasons have their own rule-bound evidence and current mute/closure checks, independent of `voiceMessagesEnabled`. Recheck policy, author access/immunity and source revocation at dispatch; never backfill old voice intents, authorize history cleanup, or substitute this proof for another content rule. Both rollback paths retain the capture/revocation reader. See `docs/operations/plans/2026-10-14-voice-webhook-deletion.md`.

## Message And Link Semantics

- User formatting arrives in `message.body.markup`, not literal Markdown. Preserve/reconstruct markup when importing, editing, or republishing.
- A forwarded message may include a supplemental `share` attachment whose URL is only a hidden preview. Publisher import must not append that URL or reject otherwise transferable text/media; use a credential-free `payload.url` only when the share is the sole transferable content.
- MAX can serve incoming photos as WebP or AVIF even though outbound image upload rejects those formats. For republishing, byte-validate first and apply the bounded JPEG/PNG normalizer only after the typed unsupported-format result.
- Publisher forward import prefers its authenticated persisted webhook receipt; a later exact-message GET is fallback only when that receipt is unavailable, because remote reads may omit nested forward content.
- A valid MAX `user_mention` markup entity is not a link-policy violation. Trust the markup discriminator, not a visible `@` label: `link` markup, unexpected `url` fields, shares, buttons, and plain HTTP(S) targets remain subject to link moderation even when their label looks like a participant mention.
- Treat `markup.from`/`length` as JavaScript string offsets in the original text; do not remap through code-point indexing on emoji-rich text.
- Resolve `max://user/<id>` labels from the full display name, including split first/last fields.
- For admin contact, prefer a direct HTTP(S) profile URL. With a saved label render `Связь с админом: [Display Name](max://user/<id>)`; without a label fall back to HTTP(S), because arbitrary-label mentions can render as plain text.
- Multi-bot links must use the same resolved `botId` for payload signing/dialog tokens and the `https://max.ru/<bot>?start=...` URL.
- Internal `startapp` links use `MAX_ENTRY_BOT_ID` with default-bot fallback, not whichever bot executes an action. Ordinary `start` links remain bot-specific.
- `startapp` payloads are limited to 512 characters and `[A-Za-z0-9_-]`; use `MaxBotLinkService`, `max-deep-link.util.ts`, and the shared launch-route patterns.
- Profile handoff payloads (`pmh-` and `pm2_`) are dedicated flows. Generic button schemas reject them, and profile caches remain route-bot-scoped.
- Trust validated `initData`/`WebAppData` with the correct bot-token HMAC only; `initDataUnsafe` is convenience data.
- Sanction explanations, warnings, and published rules append the fixed admin-contact link through dedicated `*AdminContactButtonEnabled`/`Url` fields. Mute/ban notices do not include it.
- Empty stored editable bot-speech text means inherited catalog copy; any non-empty value is custom even if it matches an old default. Never infer inheritance by string comparison.

## Publishing And Outbound Actions

- With `MAX_PUBLISHER_DISPATCH_ENABLED=false`, `api-publisher` may run identity attestation, heartbeat, webhook reconciliation, and passive lifecycle handling only; do not start publication, binding, suggestion, or chat/channel-comment recovery scans and do not probe MAX entity access.
- Publik entity discovery and user authorization are Publisher-owned. Use the exact `PublisherEntityBinding`, the Publisher bot catalog row, and a confirmed `ManagedEntityAccessEdge` whose `botId` is the Publisher bot; never require a Major `ChatBotMembership` or copy a Major access edge into this scope.
- An authenticated Publisher `bot_added` or explicit `Старт` handshake may create the shared `Chat` shell and exact Publisher catalog/binding, but must not set `Chat.botId`, `primaryBotId`, or any `ChatBotMembership`. Grant user access only after the Publisher token confirms both bot and user admin/owner access.
- `publikEnabled` is Publisher-owned and remains effectively enabled when no policy row exists. Policy reads/writes require an exact Publisher access edge, active catalog row, and binding; Major access is insufficient. A persisted `false` remains off and excludes publication target resolution, but stays visible in the Publisher cabinet for explicit re-enablement. Publisher access refresh, candidate verification, and their recovery must work while publishing is off, without writing the publication policy or sending posts.
- Mini app VK parsing routes live only under `/v1/publisher/entities/:entityType/:entityId/vk-parsing`, authorize only the Publisher profile, and require exact Publisher entity access. Do not restore the retired Major `/chats|channels/:id/vk-parsing` routes. Major settings writes, including bulk apply, must preserve Publisher-owned chat/channel-comment fields.
- VK automatic imports create their pending schedule fingerprint under the same chat policy lock as source/settings mutations, and only for newly observed posts inside the current global/source enablement baseline. Schedule changes may rekey only unattempted intents; worker deferrals after any publish attempt must preserve the original intent key and MAX ledger identity.
- A MAX-confirmed VK result whose database commit is pending is a receipt-first, database-only recovery state. Finalize it before runtime, identity, health, source, age, or content-policy guards, and never overwrite its quarantine marker from another mutation path.
- Publication HTTP handlers, occurrence dispatch, and recurring materialization are Publisher-only. Major broadcast/autopost controllers and runners are unregistered; its settings screens return an empty legacy `managedBroadcasts` compatibility field without reading broadcasts. Publication scheduling, preparation, rollup and dispatch run in `api-publisher`; the shared action role does not scan Publication work. Runtime-off skips all publication scans. `ManagedBroadcastService` execution lanes run only in the Publisher role; never restore `LEGACY_ROUTED` sends.
- Retired private-bot broadcast callbacks, start payloads, and persisted input sessions return the Publik bot link without capturing media or submitting a send. Publishing handoff HTTP routes are retired; moderation commands, rules, polls, and giveaways remain independent.
- Managed broadcast/autopost MAX calls use `MAX_API_SOURCE_TAGS.MANAGED_BROADCAST`. User sends/tests are `interactive`; scheduled/startup delivery is `background` and honors governor pause/slow decisions. Uploads stay on the send lane.
- Publication `NOW` is user-triggered even when recovered by the action poller: materialize it ahead of background work and dispatch through the immediate lane.
- Keep DB-only publication rollups outside governor pauses; ambiguous sends require manual review.
- Publisher bot snapshots remain valid until explicit loss of access. Connection roster work reuses
  the confirmed exact-bot SQL proof and retries proof supersession. Retired scheduled bot/maintenance
  jobs drain without MAX calls; publication-demand work retains its guarded coordinator lanes.
- Publisher bot and human ADMIN/OWNER grants persist until explicit MAX revocation. Read exact-bot SQL authority at commands and final effects; never expire confirmed access by `checkedAt`, `expiresAt` or launch time. Missing/partial roles, bare HTTP 403/404, 429, timeouts and 5xx preserve grants. Explicit chat/access error codes, complete validated roster absence and authenticated removal remain revocations. Retired timestamp jobs drain without MAX calls. No all-chat permission sweep; imminent preflight prepares only real work/missing candidates in `publication_access_preflight`.
- Persisted schedules without `latePolicy` keep the five-minute legacy window. New scheduled publications default to bounded 24-hour recovery, with latest-only recurring catch-up; explicit policy and retry authority apply per recipient. Never auto-replay FAILED/AMBIGUOUS effects. Modern recurrence counts include canceled slots and resume after the last durable slot in bounded batches.
- Snapshot audiences materialize all saved recipients without whole-audience access gates. A v0 pending dialog context cannot be claimed or sent; SQL permits only its untouched PENDING/zero-attempt transition to immutable v1.
