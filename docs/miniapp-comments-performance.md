# Открытие комментариев: диагностика и оптимизация

## Подтверждённая причина

До изменений холодный запуск выполнял цепочку: основной JS, клиент `/me`,
cookie-сессия, `/me`, JS/CSS экрана, запрос комментариев, отрисовка.
Экран дополнительно загружал редактор и Markdown-просмотр предложки, хотя
обычные комментарии их не используют. Проверки доступа остаются серверными.

## Реализованный план

1. Начинать предзагрузку только для точного маршрута комментариев с токеном.
   Загружать код экрана и данные одновременно с получением профиля.
2. Использовать существующий TanStack Query и тот же ключ запроса, чтобы
   монтирование экрана не делало повторный запрос. Кэш принадлежит отдельному
   клиенту текущей авторизации; смена credential очищает старый клиент.
   Уход с маршрута отменяет предзагрузку. Данные не сохраняются в localStorage.
3. Сохранить `/me` как обязательный барьер перед показом профиля и данных.
   Не менять cookie-сессии, CSRF, серверную проверку токена ветки и профиля.
4. Загружать редактор, Markdown-просмотр предложки и выбор оформления только
   при использовании. Сохранять возврат фокуса после закрытия ленивого диалога.
5. Проверять реальный production entrypoint в браузере: холодный кэш,
   замедленная сеть и CPU, отсутствие повторного запроса, независимые профили,
   размеры экранов и отсутствие неиспользуемых редакторов в сетевой загрузке.
6. Ограничивать не только размер добавки экрана, но и полный холодный путь,
   включая `/me`, сессию и предзагрузку. Общий стартовый бюджет увеличен на
   256 байт для маршрутизатора предзагрузки; бюджет добавки комментариев снижен
   с 82,5 до 67 KiB JS и с 22 до 20 KiB CSS.

## Воспроизводимая проверка

```bash
npm run check:miniapp
npm run build:miniapp:production
node apps/miniapp/test/comment-startup.browser.mjs
node apps/miniapp/test/comment-dialog.browser.mjs
node apps/miniapp/test/comment-themes.browser.mjs
```

Браузерные сценарии запускать последовательно: последние два по умолчанию
используют один dev-порт. Startup-проверка сама поднимает preview на 4178,
изолирует все внешние запросы и использует искусственные авторизацию и ответы
API. `COMMENT_STARTUP_BASELINE=1` отключает только проверки нового порядка
загрузки и ленивых редакторов для замера старой сборки. Это не измерение MAX
на реальном устройстве и не production p95. Снимки сохраняются в `/tmp`.

В исходном сравнении при 120 мс сетевой задержки, 1,5 Мбит/с, CPU x4 и
450 мс искусственной задержки каждого API-запроса старая сборка показывала
комментарии за 4,0–4,5 с. После перекрытия загрузок первый повторный замер
составил около 2,9 с. До изменения запрос комментариев начинался примерно
через 1,2 с после ответа `/me`; после изменения запросы перекрываются.

## Следующие Этапы По Метрикам

- Измерить p50/p95 открытия внутри настоящих MAX WebView отдельно от времени
  API, DNS/TLS и размера ресурсов. Не записывать initData, токены веток,
  идентификаторы или тексты комментариев в метрики.
- Для больших каналов Майора проверить план фильтрации `audit_logs` по ветке:
  существующий запрос использует JSON `threadId` и индекс chat/action/time,
  но не отдельный индекс ветки, уже имеющийся у Публика. При подтверждённой
  задержке добавить частичный expression index и согласованный SQL-предикат,
  тест generic plan на локальном PostgreSQL и отдельную concurrent-миграцию.
  Не выполнять EXPLAIN ANALYZE или широкие сканирования production.
- При росте нагрузки от опроса каждые 8 секунд оценить курсорное обновление
  и условные ответы. SSE требует измерений, восстановления соединения,
  повторной авторизации и лимитов; сам по себе он не ускоряет холодный запуск.
- Виртуализацию вводить только после измерения длинных лент: текущий API
  ограничивает ответ 80 сообщениями. Не добавлять service worker или общий
  долговременный кэш приватных ответов ради показателей первого экрана.

Эта поставка меняет только `miniapp-major-static`; миграций и пересоздания
API/Postgres/Redis не требует. Выкладка проходит через exact-SHA CI и обычный
VPS wrapper, затем проверяется `https://major-maksimov.ru/app/`.
