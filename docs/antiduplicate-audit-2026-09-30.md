Проверены исходники и production API image на
`cfb93bae1ae730110c05e4c8290e0ab7f391c35c`. В проверенном снимке 30 сентября
runtime-антидубль работал в `full`, revision 2, `all_enabled_chats`, без срока истечения. Аудит выявил
семь недостатков: четыре ошибки поведения, ошибку повторного планирования
при нагрузке и два дефекта диагностики. При доработке плана дополнительно
воспроизведена потеря запрета действий после истечения ordering-записи, пункт 8.
Исправления в этом документе не реализованы. Порядок работ, дополнительные риски
и условия выпуска описаны в [плане исправлений](antiduplicate-repair-plan-2026-09-30.md).

## Подтверждённые Недостатки

### 1. P1: Отозванное основание восстанавливается после правок A -> B -> A

`lifecycle` хранит только последнюю пару времени и содержимого. Когда обычная
обработка антидубля пропущена после раннего выхода из модерации, изменения не
инвалидируют сохранённую `message`-запись необратимо. Возврат к прежнему содержимому
делает старое основание снова действительным: `valid()` и `matching()` сравнивают
текущий source digest, но не историю его замены.

Воспроизведены два сценария с настоящим Redis: правки оригинала и правки самого
дубля. После A -> B `stillMatches()` возвращает false, после B -> A возвращает
true для прежней binding. Ожидается false в обоих случаях. Такой путь существует,
поскольку `observeLifecycle()` вызывается до ранних выходов, а `observe()` позже.
Обычный тест с полным `observe()` каждой правки эту ошибку не обнаруживает.

Источники: `apps/api/src/moderation/message-duplicate/message-duplicate-window.script.ts:30`,
`:49`, `:64`; `apps/api/src/moderation/moderation.service.legacy.ts:1348`, `:2235`.
Нужна монотонная версия содержимого либо постоянный отзыв старого состояния при
содержательной правке; возврат текста не должен возвращать старые полномочия.

### 2. P1: Поздний запрет действий у задания не останавливает удаление

Поглощающий `actionEligible=false` проверяется перед `enforcement.enqueue()`.
Дальше передаётся только `lease.assertOwned`: владение блокировкой не означает,
что действия всё ещё разрешены. Внутри сохранения intent и последующих guards
флаг может смениться на false, но проверка разрешения больше не выполняется.
Привязка intent также не содержит этого запрета для последующего dispatch.

В сквозном воспроизведении после успешной проверки картинки
`ensureIntentWithMessageActionClaim()` выполняет `ordering.announce(identity, false)`
перед возвратом сохранённого intent. Блокировка остаётся действующей. Ожидается
отсутствие удаления; фактически повтор удаляется. Проверка изолирует отзыв флага:
конкурирующая политика в этом сценарии сама не создаёт отдельный action claim.

Источники: `apps/api/src/moderation/message-duplicate/message-duplicate-media.service.ts:362`,
`:382`; `apps/api/src/moderation/message-duplicate/message-duplicate-enforcement.service.ts:133`.
Нужна проверка актуального разрешения перед квалификацией и каждым действием,
а также сохранение отзыва для уже созданного intent и его восстановления.

### 3. P1: Пауза governor повторяется каждые 5 секунд и задания теряются по сроку

Media service выбрасывает ошибку без `decision.retryAfterMs`. Processor назначает
всем таким случаям повтор через 5000 ms. Для production governor настроено
180000 ms. В результате одно отложенное задание опрашивается до 120 раз за
десятиминутный срок вместо соблюдения рекомендованной паузы. Задания того же чата
также повторяют попытки из-за порядка обработки. Истёкшее задание завершается
без проверки картинки, учитывается отдельно как `worker.expired` и не восстанавливается.

Это наблюдалось на VPS: в одном 30-секундном интервале было 6953 начала попыток,
6112 отсрочек порядка, 823 отсрочки media, 7 завершений и 11 истечений срока.
Счётчики отражают попытки, а не число уникальных сообщений. В отдельном снимке
было 1259 delayed, 25 waiting, 2 active; возраст самого старого из 20 выбранных
delayed-заданий составлял 574 секунды. Позже load ratio был 1.346 при pause-пороге 1.25.

Источники: `apps/api/src/moderation/message-duplicate/message-duplicate-media.service.ts:239`;
`apps/api/src/moderation/message-duplicate/message-duplicate.processor.ts:69`, `:114`;
`infra/docker-compose.yml:442`.
Нужно переносить причину и срок отсрочки из governor, различать её с readiness/order
и обеспечить продвижение очереди без частого опроса каждого ожидающего задания.
Продление общего срока само по себе не исправит повторную нагрузку.

### 4. P2: Правка подписи оригинальной картинки сбрасывает допуск и наказания

IMAGE admission сначала записывает непроверенную identity. Для нового времени
правки replay допускает пустую identity только при равенстве старого времени.
Поэтому даже неизменившаяся картинка временно теряет проверенное состояние.
Повторное вычисление хеша создаёт основание с новым `observedAtMs`. Время публикации
сохраняется, но ключ счётчика включает `original.observedAtMs`, и счётчик начинается заново.

Два сквозных воспроизведения с настоящими Redis, очередью и Sharp:

- оригинал, повтор с WARN, изменение только подписи оригинала, следующий повтор:
  ожидается MUTE, фактически WARN;
- допуск одного повтора, оригинал, разрешённый повтор, изменение только подписи,
  следующий повтор: ожидается удаление, фактически сообщение остаётся.

Подпись по правилам IMAGE не входит в сравнение. Такие правки позволяют снова
получать допуск и начинать лестницу наказаний в том же окне.

Источники: `apps/api/src/moderation/message-duplicate/message-duplicate.service.ts:127`;
`apps/api/src/moderation/message-duplicate/message-duplicate-window.script.ts:60`, `:107`, `:123`.
Неизменившееся сравниваемое содержимое должно сохранять идентичность основания
и счётчики при повторной проверке медиа.

### 5. P2: DAILY ошибочно включает содержимое, изменённое вне периода

Вне ежедневного периода `observe()` возвращается до обновления истории.
`observeLifecycle()` сохраняет digest, но не время введения новой версии.
При следующей косметической правке внутри периода Lua сравнивает содержимое со
старой `message`-записью и назначает временем публикации текущую правку.

Воспроизведение для DAILY 09:00-18:00 UTC:

1. Вчера в 12:00 опубликован текст A.
2. Сегодня в 08:00 он заменён на B, вне периода.
3. В 10:00 у B изменён только пробел, сравниваемое содержимое то же.
4. В 10:00:00.100 отправлен новый B. Он удалён на основании старого сообщения.

B был введён в 08:00 и не должен становиться сегодняшним основанием через
косметическую правку. Даты в диагностическом тесте были фиксированы на
1-2 октября 2026, чтобы виртуальные часы не нарушали deadline настоящего Redis.

Источники: `apps/api/src/moderation/message-duplicate/message-duplicate.service.ts:83`;
`apps/api/src/moderation/message-duplicate/message-duplicate-window.script.ts:113`.
Нужно сохранять время содержательной версии независимо от доступности действий
в текущем периоде и использовать его при последующем допуске.

### 6. P2: Новая очередь отсутствует в системной панели

В `AUXILIARY_QUEUE_NAMES` присутствует retired `PHOTO_DUPLICATE_QUEUE`, но нет
активной `MESSAGE_DUPLICATE_QUEUE`. Общий dashboard формирует сведения об
auxiliary queues только из этого списка. Поэтому backlog и failed действующего
антидубля не попадают в эту часть системной панели. VPS `monitor-readonly`
очередь уже знает, поэтому проблема относится именно к dashboard/read model.

Источник: `apps/api/src/system/queue-metrics.service.ts:63`, `:538`.
Нужно добавить активную очередь в закрытую диагностику и проверить её отображение.
Расширять лёгкие публичные readiness-запросы полным обходом очередей не требуется.

### 7. P2: SQL-аудит сообщает активность картинок по retired-настройкам

`photo_effective_enabled` по-прежнему считается как
`anti_duplicate_enabled AND duplicate_photo_enabled`; выборка preset также
фильтруется старым выключателем и показывает retired `MINOR_EDITS`.
Новый IMAGE runtime определяется master switch, `duplicateCompareMode`, scope
и runtime authority; старый photo toggle/preset им не управляет.

Production-аудит вывел 111 как нижнюю границу «effectively enabled» по старой
формуле. Это число не описывает активный IMAGE-путь. Выборка из 5000 настроек
насыщена, поэтому реальное количество всех включённых чатов не установлено.

Источник: `infra/scripts/vps-postgres-audit.sh:1000`, `:1020`, `:1032`.
Нужно разделить поля совместимости и текущую eligibility, учитывать compare mode
и отдельно показывать проверенный runtime mode, сохранив ограничение выборок.

### 8. P1: Истечение ordering-записи снимает поглощающий запрет действий

`PENDING_TTL_MS` равен пяти минутам. Очистка expired-заданий в `ANNOUNCE_SCRIPT`
удаляет не только pending/member, но и `action-eligibility`. Следующая регистрация
того же job с `true` видит отсутствие сохранённого запрета и снова разрешает
действия. Само задание может жить десять минут; перезапуск или длительное ожидание
оставляют возможность повторной попытки после потери latch.

При доработке плана выполнен отдельный локальный probe настоящего Lua из исходника
на Redis 7.0.15, loopback:16392, без persistence. Последовательность true -> false
-> true до expiry дала 1 -> 0 -> 0. После переноса только score этого job в expiry
в прошлое, имитирующего истечение пяти минут, следующая регистрация с true дала 1.
Проверка подтверждает потерю запрета в хранилище; сквозное удаление после такого
простоя в этом дополнительном probe не выполнялось. Скрипт и локальные ключи
удалены, Redis остановлен без сохранения данных.

Источники: `apps/api/src/moderation/photo-duplicate/photo-duplicate-ordering.store.ts:9`,
`:19`, `:27`, `:51`; `apps/api/src/moderation/message-duplicate/message-duplicate.processor.ts:69`.
`MessageDuplicateOrderingStore` наследует этот Lua в отдельном namespace.
Запрет нужно хранить независимо от технического порядка очереди и сохранять
до конца срока всех действий, которым данное задание могло передать полномочия.

## Дополнительные Production-Наблюдения

Проверки health/live и readiness прошли, Postgres и Redis отвечали; обычный
webhook lag составлял около 0.4 секунды. Это не доказывает здоровье отдельной
очереди картинок. Проверенные api-admin, api-action и api-moderation-background
работали на одном указанном выше полном SHA.

В 50 последних сохранённых failed-заданиях найдены 30 `Photo URL is not permitted`,
18 MAX HTTP 404 и 2 превышения лимита байтов. Это ограниченная выборка failures,
а не частота ошибок среди всех сообщений. URL, токены, тексты и идентификаторы
пользователей в аудит не выводились. Причина запрета URL не установлена:
проверка включает HTTPS, credentials, порт и allowlist. Настройка
`MESSAGE_DUPLICATE_ALLOWED_HOSTS` используется binary downloader; фотографии
идут через downloader с `PHOTO_DUPLICATE_ALLOWED_HOSTS`. Значения по умолчанию
различаются, что следует учитывать при дальнейшей проверке источников.

`postgres-audit duplicate` успешно вернул ограниченные настройки и moderation
events, но запрос delete intents прервался по `statement_timeout`, exit 3.
Полная статистика удалений и причины каждой пользовательской жалобы не установлены.
Настройки, очереди, сообщения и санкции production не изменялись.
