# Антидубль: локальные замеры фото и чтения proofs

Дата: 4 октября 2026. Node 24.16.0, Linux/WSL, один последовательный исполнитель.
Эталон checkpoint: `1333fa9295506f2bff66df8c97cee17124931dcc`; новая реализация:
`c3c644c6`, изоляция native: `ed258842`. Замеры не описывают производственную
пропускную способность, Docker RSS или задержку MAX.

## Checkpoint альбома

Один и тот же альбом из двух изображений проходит два вызова настоящего
`PhotoDuplicateAnalysisService`: во время первой попытки загрузка второго
изображения возвращает контролируемую временную ошибку; второй вызов завершается.
Загрузчик изолирован, декодирование выполняет настоящий Sharp. Кеш каждой пары
попыток начинается пустым. Варианты чередуются до/после и после/до; первые четыре
пары отброшены, следующие 40 учтены.

Изображение: RGBA 1024 × 768; байт с индексом `i` равен
`(i * 13 + floor(i / 4096) * 7) % 256`. PNG из Sharp: 23 822 байта.
Canonical hash и итоговый album hash совпали во всех сравнениях.

| Показатель на пару попыток |    До | После |
| -------------------------- | ----: | ----: |
| Обращения к загрузчику     |     4 |     3 |
| Успешные native decode     |     3 |     2 |
| p50, мс                    |  9,83 |  6,73 |
| p95, мс                    | 14,28 |  9,83 |

Таймер включает обе попытки. Задержка сети не моделировалась. Количественное
сокращение повторной работы подтверждено также регрессионным тестом. Ошибка
checkpoint-записи допускает повторное вычисление; она не превращает неполный
альбом в доказательство совпадения. Кешированные byte/pixel costs повторно
занимают бюджет альбома при возобновлении.

## Цена изоляции native

На том же изображении сравнивались прежний in-process Sharp и собранный
`native-photo-worker.js`, включая запуск процесса, stdin/stdout и подтверждённое
завершение process group. Четыре прогрева, 20 измеряемых пар; hashes совпали.

| Путь              | p50, мс | p95, мс |
| ----------------- | ------: | ------: |
| In-process        |    4,68 |    5,36 |
| Отдельный процесс |   51,62 |   65,52 |

Изоляция ограничивает зависания и воздействие native-кода и имеет измеряемую
стоимость. Она не заявляется ускорением. Отдельный UDS smoke собранной реализации
с реальным worker в Linux `unshare -Urn`, без внешних интерфейсов и с пустым
исходным окружением, прошёл за 56,8 мс. Проверка Docker cgroup-лимитов локально
не выполнена: Docker daemon недоступен; она обязательна при выпуске.

## Чтение Redis proofs

Настоящий локальный Redis, Unix socket, без искусственной сетевой задержки.
Для каждого варианта 100 прогревочных и 1000 измеряемых пар; порядок вариантов
чередовался. Cold — все ключи отсутствуют, warm — все содержат одинаковый
корректный JSON proof с EX 3600. Значения и порядок совпали, TTL не продлевался.

| Фотографий | Кеш  | Последовательные GET p50/p95, мс | Pipeline GET p50/p95, мс |
| ---------- | ---- | -------------------------------: | -----------------------: |
| 1          | cold |                    0,040 / 0,122 |            0,041 / 0,119 |
| 1          | warm |                    0,038 / 0,136 |            0,038 / 0,138 |
| 10         | cold |                    0,342 / 0,719 |            0,052 / 0,124 |
| 10         | warm |                    0,343 / 0,616 |            0,054 / 0,104 |

Принято только объединение независимых proof GET одного сообщения/ревизии в
pipeline до десяти ключей. Число Redis-команд остаётся десять, число обменов
сокращается с десяти до одного; одиночное чтение использует прежний GET.
Ошибки GET, включая WRONGTYPE, сохраняются. MGET здесь непригоден: он возвращает
`null` для значения неподходящего типа и меняет обработку повреждённого кеша.
Новый кеш, изменение TTL, новая область доступа и объединение действий разных
запросов не вводились.

IMAGE-кандидат содержит ровно один ключ независимо от числа фотографий.
Его чтение не менялось: выгоды от batching нет. Другие кандидатные чтения
перемежаются условными записями; они не включены в эту оптимизацию.
