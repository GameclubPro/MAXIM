# Антидубль: воспроизводимая локальная проверка нагрузки

Дата: 4 октября 2026. Проверенный runtime: `0e9d7aaa04c15492770d05f0d4596daef2607932`.
Node 24.16.0, Linux/WSL, Redis 7. Проверка выполнена; все 13 сценариев прошли.
Она дополняет production smoke и измерения оптимизации, но не устанавливает
производственный QPS или SLO.

## Исполняемая проверка

`apps/api/test/message-duplicate-capacity.node.cjs` использует собранные классы
`MessageDuplicateProcessor`, enqueue/ordering, историю сообщений, photo analysis,
`SecurePhotoDownloader`, fingerprint service и настоящий native UDS client/server.
BullMQ, Redis, Lua, PNG-декодирование, subprocess teardown и network namespace
настоящие. Native запускается через `unshare -Urn`; сервер самостоятельно проверяет
отсутствие внешних интерфейсов, его окружение очищается. Подмена проверки сети
или native worker не используется.

Изолированы две зависимости: durable SQL admission заменён локальной регистрацией,
а DNS/HTTPS transport возвращает детерминированный PNG, HTTP 503 или управляемый
барьер. Внешних запросов и MAX-действий нет. Обработка заканчивается сравнением
истории: квалификация, SQL cleanup obligations, delete intents и dispatch сюда
не входят. Поэтому `actionEligible` отключён. PostgreSQL создаёт общая штатная
обёртка, но эта проверка его не использует.

В чистом checkout после установки зависимостей:

```bash
timeout --kill-after=10s 540s npm run build --workspace @maxim/api
timeout --kill-after=10s 540s node scripts/agent/with-test-stores.mjs -- \
  node scripts/with-file-lock.mjs api-validation -- \
  node apps/api/test/message-duplicate-capacity.node.cjs
```

Сначала обязательна успешная сборка именно проверяемого checkout: harness читает
`dist`, не компилирует runtime скрыто. Нужны локальные PostgreSQL 16/Redis 7,
`unshare`, `getconf` и доступный user/network namespace. Docker не требуется.
Harness отказывается от не-loopback URL и непустого Redis, ограничивает обход
4096 ключами/100 страницами, удаляет только созданные ключи/очередь и собственный
namespace-процесс. Обёртка удаляет временные хранилища. JSON со скалярами выводится
одной строкой `CAPACITY_RESULT`; идентификаторов сообщений и содержимого в нём нет.

## Равномерный поток и горячий чат

В каждой ячейке одинаковый конечный burst: 16 сообщений с одним или десятью фото.
Равномерный вариант — четыре чата по четыре сообщения; перекошенный — горячий
чат с 12 сообщениями и спокойный с четырьмя. Авторы чередуются, отдельно проверены
`SAME_AUTHOR` и `CHAT`. Два реальных BullMQ worker slots, один native slot,
стандартные лимиты фото. Общая фиксированная пятисекундная задержка начального
settlement исключена одинаково из обоих вариантов до старта worker.
Это не генератор открытого потока и не проверка устойчивости на длительном QPS.

PNG: 512 × 384 RGBA, 6782 байта; байт `i` равен
`(i * 13 + floor(i / 4096) * 7) % 256`. На строку с одним фото передано 108 512
байт и выполнено 16 загрузок; с десятью — 1 085 120 байт и 160 загрузок.
Повторных загрузок в матрице не было. Все 144 jobs, включая отдельный сценарий
заблокированного источника, завершились, без failed/waiting/delayed/active остатка.

| Фото | Область     | Равномерный burst, мс | Горячий + спокойный, мс | Спокойный чат завершён, мс |
| ---: | ----------- | --------------------: | ----------------------: | -------------------------: |
|    1 | SAME_AUTHOR |                   795 |                     768 |                        341 |
|    1 | CHAT        |                   755 |                     761 |                        333 |
|   10 | SAME_AUTHOR |                  7455 |                    7520 |                       3654 |
|   10 | CHAT        |                  7479 |                    7571 |                       3734 |

Время отсчитывается от начала admission; burst — время завершения сценария.
Это единичный локальный прогон по 16 сообщениям на ячейку. В JSON есть sample
p50/p95; p95 из 16 элементов практически равен максимуму и не является оценкой
производственного p95. Порядок вариантов фиксирован, сравнение не обосновывает
ускорение одной конфигурации относительно другой.

Во всех перекошенных вариантах спокойный чат завершился до опустошения горячего.
Дополнительная детерминированная проверка удерживает первое фото горячего чата
до завершения всех четырёх сообщений спокойного. Они завершились за 208 мс
до освобождения барьера; ни один следующий hot job не обошёл своего первого.
После освобождения завершились все 16. Это доказательство отсутствия блокировки
другого чата в проверенном сценарии, не обещание справедливости при произвольном
числе горячих чатов или длительном перегрузе.

## Ресурсы и история

Ресурсы измеряются отдельно от решений модерации. CPU основного процесса —
`process.cpuUsage`; native CPU — изменение Linux `utime/stime/cutime/cstime`,
100 ticks/s на этой машине. RSS дерева sandbox/worker снимается каждые 20 мс,
поэтому короткий пик может быть пропущен. Это RSS, не cgroup memory peak.

Для 16 сообщений с десятью фото API-процесс использовал 189–307 CPU-мс,
включая orchestration и измерители; native — 8,33–8,42 CPU-с. Наблюдаемый максимум
RSS native-дерева — 130–137 MiB. CPU-с могут превышать wall time: локальная
проверка не задаёт cgroup CPU cap. Не переносить эти цифры на VPS с лимитом 1 CPU.
Полный API-процесс включает загруженные Nest/BullMQ/Prisma модули, а не только
маргинальную память антидубля; JSON явно хранит его отдельным полем.

В матрице после удаления тестовой BullMQ-очереди осталось 74–80 ключей при одном
фото и 218–224 при десяти; соответственно около 52–54 KiB и 127–130 KiB
по сумме `MEMORY USAGE`. Все application keys имели TTL. 3013–3431 Redis-команда
на сценарий включают внутренние команды Lua/BullMQ и инспекцию; это не число
сетевых обменов и не число GET. Значения не используются для оценки batching.

Отдельно 256 оригинальных наблюдений истории, восемь авторов и одинаковое
изображение, затем точный повтор всех наблюдений:

| Область     | 64 сообщения: ключи | 128 | 256 | После 256 повторов | Redis bytes при 256 |
| ----------- | ------------------: | --: | --: | -----------------: | ------------------: |
| SAME_AUTHOR |                 144 | 272 | 528 |                528 |              544896 |
| CHAT        |                 137 | 265 | 521 |                521 |              543016 |

Подтверждён линейный рост по числу новых сообщений и отсутствие роста при точном
повторе, а не абсолютный лимит истории на чат. TTL ограничивает время хранения;
эта проверка не доказывает допустимость памяти при любом входящем потоке.
Десять отдельных proofs с TTL=1 с исчезли за наблюдаемые 1005 мс без чтения,
продлевающего TTL. Это проверка механизма Redis expiry, не скорость SQL cleanup
reconciler и не проверка фактического производственного TTL в течение суток.

## Ошибка источника и восстановление

HTTP 503 на десятом фото оставляет девять proofs. Следующая попытка завершает
альбом: всего 11 обращений к загрузчику, десять успешных передач, 67 820 байт.
Сто следующих попыток возвращают тот же полный fingerprint и сохраняют ровно
десять Redis proofs, 4880 bytes; новых загрузок нет. Неполный альбом не попадает
в историю и не становится доказательством совпадения.

Этот сценарий проверяет checkpoint photo store, где существующий batch reader
использует MGET. Он не является замером новой pipeline-оптимизации общего
media-proof reader; её отдельное сравнение находится в
`docs/antiduplicate-photo-benchmarks-2026-10-04.md`.

## Границы допуска

Локально не доступны Docker daemon и Tesseract. Здесь не измерены одновременно
работающие OCR/photo контейнеры, их cgroup CPU/RSS, production QPS, длительный
hot-chat fairness, MAX latency и скорость durable SQL cleanup. Проверка не
даёт оснований повышать concurrency, увеличивать лимиты или обещать полную
изоляцию затрат OCR на этом основании. Для общего OCR/photo допуска нужны
отдельные реальные контейнеры из того же образа и сопоставимые solo/combined
фикстуры; контроль boundary и recovery остаётся в штатной Docker CI lane.
