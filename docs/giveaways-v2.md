# Розыгрыши V2: аудит и план развития

## Продуктовая модель

Пост в MAX отвечает за предложение: призы, изображение, описание и правила.
Мини-приложение отвечает за участие: условия, достоверный статус проверки,
сроки, заявку и подтверждение выигрыша. Каталог призов и обложка не дублируются.
Открытие экрана само по себе не регистрирует заявку. Один MAX user ID получает
одну запись участия; число заявок не равно числу уже проверенных участников.

## Обнаруженные проблемы

1. Экран участника вырос в модальное окно с вложенными карточками и ещё одним
   окном деталей. Призы оттесняли главное действие; обязательные подписки были
   видны только после отказа. Нулевой список отсутствующих подписок ошибочно
   превращался в полный прогресс даже без проверки.
2. Несколько независимых путей повторной проверки могли пересекаться; ошибки
   после сохранения заявки выглядели как неудачное вступление. Отображение
   времени зависело от часов устройства, а действие подтверждения могло остаться
   доступным после истечения срока.
3. Вступление проверяло дедлайн до сетевой проверки MAX, но не при записи.
   Получение приза и административные переходы обновляли победителя по ID без
   сравнения состояния после удалённой проверки.
4. Розыгрыш имел устаревающую блокировку, но запись итогов не проверяла владение
   этой блокировкой. Обработчик ошибки мог освободить чужую блокировку. Обновления
   всех заявок запускались одновременно; время получения приза отсчитывалось
   от начала проверки аудитории, а не от фиксации итогов.
5. Кабинет показывал текущий или последний розыгрыш без выбора предыдущих.
   Публикация не имела отдельного финального подтверждения параметров.
6. Создание проверяло отсутствие другого розыгрыша вне транзакции; два запроса
   могли создать два черновика. Публикация старого черновика не отклоняла уже
   прошедший срок завершения.

## План реализации

### Этап 1. Новый сценарий участника

- Полноэкранная, прокручиваемая страница вместо псевдомодального окна.
- Постоянный список источника и обязательных подписок, без дублей.
- Состояния каждого условия: неизвестно, проверяется, выполнено, отсутствует.
  Ошибка транспорта не является отсутствием подписки. Переход по ссылке не
  является подтверждением подписки.
- Одна явная команда проверки и регистрации; одна проверка при возвращении
  после открытого условия. Никаких искусственных процентов или выигрышей.
- Анимированный индикатор проверки и короткое подтверждение успешной заявки;
  reduced-motion отключает декоративное движение. Тактильная обратная связь
  через существующий MAX Bridge.
- Серверное время как опорная точка таймера; обновления только на видимом экране.
  Отдельные состояния до старта, приёма заявок, подведения итогов, отмены,
  завершения, выигрыша, подтверждения и истечения срока.
- Число заявок и число мест, ссылка на исходный пост, персональный номер заявки,
  время последней проверки. Призовые названия остаются в посте.
- Ошибки доступны рядом с действием, с повтором; данные предыдущего запроса не
  маскируют ошибку проверки. Победители показаны без публичных пользовательских ID.

### Этап 2. Целостность серверной модели

- Создание сериализуется SQL-транзакцией; устаревший черновик не публикуется.
- Проверка членства выполняется вне SQL-транзакции. Запись заявки выполняется
  под условным обновлением родительского розыгрыша с повторной проверкой дедлайна.
- Изменение черновика требует DRAFT и отсутствия отправки в момент записи.
  Отмена не может перебить DRAWING или незавершённую отправку.
- Подтверждение, выдача и замена победителя используют compare-and-set текущего
  статуса; подтверждение повторно проверяет срок после MAX.
- Финализация записывает заявки и победителей только при совпадении draw seed
  и токена блокировки; просроченный исполнитель не изменяет чужие итоги.
- Сбой освобождает только собственную блокировку. Время подтверждения начинается
  при фиксации победителей. Сохраняются существующие криптографическое ранжирование,
  повторная проверка подписок, журнал отправок и outbox уведомлений.
- Контракт сообщает время сервера и последней проверки, совместимо со старым UI.

### Этап 3. Кабинет организатора

- Существующий редактор сохраняет рабочие поля и MAX-совместимые дату, время,
  изображение и проверку внешних каналов.
- Выбор текущего и исторических розыгрышей, обновление незавершённых состояний.
- Перед отправкой: подтверждение начала, конца, числа мест и обязательных
  подписок. Это не имитация уже отправленного поста.
- Опасные действия остаются с подтверждением. Завершённые результаты доступны
  независимо от наличия нового активного розыгрыша.

### Этап 4. Проверка и поставка

- Регрессии для времени, неизвестных условий, повторного вступления, истёкшего
  подтверждения, конфликтов состояния и устаревшего исполнителя.
- Проверки API, контрактов и обоих UI-потребителей. Продакшен-сборка мини-приложения.
- Playwright: iPhone SE, iPhone, Android и desktop, светлая/тёмная темы,
  отсутствие горизонтального переполнения, доступность действий после скролла,
  неизвестные/отклонённые/подтверждённые условия, победитель, истёкший срок,
  отказ API и возврат из MAX.
- Поведенческий прогон на локальном Vite: `node apps/miniapp/scripts/check-giveaway-browser.mjs`.
  По умолчанию используется `http://127.0.0.1:5174/app/`; другой адрес задаётся
  через `MINIAPP_GIVEAWAY_TEST_BASE`. Изолированный HTML/React fixture находится
  в `apps/miniapp/test/browser/` и не входит в продакшен-сборку.
- Выкладка только собственного проверенного коммита с зелёными exact-SHA CI,
  затем все API-роли и затронутые статические компоненты штатным deploy wrapper.
  Чужие staged-изменения и миграции не включаются в релиз автоматически.

## Следующие релизы до уровня большого специализированного сервиса

Это отдельные работы, а не заявленные возможности текущей версии.

1. Масштабирование: отдельный public read model без обложки/base64 и полной
   аудитории, индексные счётчики, cursor-история, пакетный checkpointed draw,
   ограниченный fanout MAX и SQL. Цель: ответы GET не растут линейно с аудиторией;
   нагрузочные прогоны на 1k/10k/100k заявок без влияния на модерацию.
2. Проверяемая честность: до старта публикуется commitment секрета, после дедлайна
   фиксируется псевдонимизированный список допущенных заявок и его hash; после
   draw раскрывается seed и версия алгоритма. Независимый verifier повторяет
   результат. Нужна защита от выбора seed организатором, правила энтропии и
   приватности. Текущее серверное случайное ранжирование не называем публично
   доказуемым. Повторные выборы публикуются как отдельные протоколы с причиной.
3. Антифрод: ограничения частоты по пользователю/розыгрышу, журнал аномалий,
   индивидуальные объяснения дисквалификации и апелляция. Не обещать проверку
   возраста аккаунта, репоста или иных сигналов, которых MAX API не предоставляет.
4. Организатор PRO: шаблоны, дублирование в новый черновик, полнотекстовый поиск,
   фильтры, выгрузки с минимизацией персональных данных, роли и журнал действий,
   воронка открытие -> проверка -> заявка -> допуск -> подтверждение -> выдача.
5. Надёжность: PostgreSQL race-тесты на реальной БД, инъекции отказов между MAX
   отправкой и SQL receipt, SLO для вступления и задержки итогов, сигнализация
   застрявших draw/outbox, retention персональных данных и правила хранения.

## Критерии готовности

Ни один непроверенный пункт не зелёный. Открытие ссылки не меняет допуск.
После дедлайна нельзя дописать заявку или подтвердить истёкшее место.
Старый worker не перезаписывает новые итоги. Двойное нажатие не создаёт второй
билет. Сбой MAX не превращается в выдуманный результат. Призовые сведения
не занимают экран участия. Все незавершённые проверки и поставка отражаются
отдельно в отчёте, без обещания найти абсолютно все возможные дефекты.
