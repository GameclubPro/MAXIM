# VK-предложка в личке Publisher

## Подключение

Функция доступна для каналов Publisher. Администратор открывает «Согласование в личке»
в VK-модуле, переходит по кнопке в точного Publisher-бота (`start=vk_review`)
и нажимает «Получать мне». Команда `/vk` в том же боте также подтверждает личку
и открывает список подключённых каналов. Получатель берётся из проверенной личности,
произвольный пользователь или private chat id через HTTP не принимается.

Ссылки подключения и кабинета строятся через Publisher-specific методы
`MaxBotLinkService` по дескриптору Публика. В `api-admin` Publisher намеренно
отсутствует в списке исполняющих ботов; общий action-route fallback для этих
ссылок запрещён. Токен Публика для построения URL не нужен.

Для нужных источников выбирается режим «Личка» (`BOT_REVIEW`). Старый `REVIEW`
сохраняет отдельную проверку через закрытый Safety Desk. Первичная загрузка и первый
успешный sync не создают предложений. Следующие sync создают задания только для
впервые замеченных записей с датой VK не раньше `botReviewEnabledAt`.
Старый пост можно явно отправить кнопкой «В личку на согласование».

## Семантика

- Один согласующий на канал, несколько каналов в одной личке.
- Превью с полным текстом и поддерживаемыми медиа отправляется отдельно от
  служебного сообщения. Кнопки приходят ответом на точное сообщение-превью.
- «Опубликовать» разрешает существующую асинхронную VK-публикацию сейчас.
  «Принят в публикацию» не означает подтверждение MAX; ссылка появляется по receipt.
- Отказ относится к одному каналу и не сбрасывается повторным импортом.
- Максимум пять открытых карточек на канал и десять на получателя. Неопределённые
  доставки занимают слот, поскольку сообщение могло дойти.
- Доставка в личку работает круглосуточно: рабочие и тихие часы публикаций на неё
  не влияют. Явная пауза согласования, пауза импорта и фоновый governor сохраняются.
  Пауза доставки не запрещает явно одобрить уже полученный пост и не удаляет очередь.
- Снимок содержит подготовленный текст, медиа и fingerprint исходного содержимого
  и настроек обработки. Изменение до отправки требует повторного согласования.
- Редактирование ожидающего поста доступно в VK-ленте мини-аппа. После изменения
  старая карточка предлагает обновить превью; старые версии кнопок не действуют.

## Исполнение И Восстановление

`vk_bot_review_inboxes` хранит подтверждённую пару Publisher/user и личный диалог.
`vk_bot_reviews` хранит единственное задание на VK-пост, снимок и версию,
отдельные состояние решения и состояние доставки, обе квитанции MAX.

Импорт создаёт задания внутри существующей транзакции с блокировкой канала.
Работа `kind=vk-bot-review` использует `publisher-suggestion-admin`; единственный
worker `api-publisher` последовательно обрабатывает карточки и решения с приоритетом
интерактивных действий. Tick выбирает до десяти строк каждого состояния отдельным
индексным проходом, отдавая приоритет незавершённым парам сообщений. Он делает
не более одного шага на получателя и пяти получателей за проход, следующий проход
планируется через пять секунд. Заполненный канал не блокирует следующий канал.
После незавершённых пар остальные задания выбираются по `nextAttemptAt`; при
одинаковом сроке новая доставка опережает служебное обновление уже открытой карточки.
Просроченное восстановление одобрения при этом не вытесняется более новыми заданиями.
Если текущих заданий ещё нет, tick сохраняет пробуждение на ближайший
`nextAttemptAt` отдельными индексными чтениями по состояниям. Иначе обновление
первой доставленной карточки могло на каждом проходе scheduler снова откладывать
остальные: обработчик засыпал раньше их срока, и следующая карточка приходила
только после решения по первой. Пустая очередь, terminal-срок `9999-01-01` и
`AMBIGUOUS` не запускают постоянный опрос; лимиты открытых карточек сохранены.
`VkParsingRunnerService` восстанавливает потерянный tick через текущий VK scheduler.

При запуске новый runtime ограниченными пачками освобождает старые календарные
отсрочки: только `PENDING` в `QUEUED`/`ERROR`/`CONTENT_SENT`, записанные до запуска,
дальше максимального технического повтора и раньше terminal-срока. Технический
предел учитывает пятиминутный retry и настроенную паузу governor. Меняется только
`nextAttemptAt` с проверкой прежнего значения и версии; leases и `AMBIGUOUS`
не затрагиваются, паузы и права повторно проверяются перед отправкой.

До каждого POST в MAX состояние отправки фиксируется в БД. Зависшая подготовка
может повторяться; зависшие `CONTENT_SENDING`/`CONTROL_SENDING` становятся
`AMBIGUOUS` и автоматически не повторяются. Известная квитанция повторно сохраняется
без повторного POST. Неопределённую доставку нельзя сбросить публичным API.
Структурированный ответ MAX с однозначным отказом (например, `chat.denied`/403
или лимит/429) оставляет доставку повторяемой; неизвестные ошибки и 5xx этого не делают.
При обращении пользователя сначала проверить факт доставки; не очищать эти состояния
массовым SQL и не запускать ручную повторную публикацию без проверки MAX.

В канале публикация использует существующую очередь `vk-parsing-publisher`, точного
Publisher и существующий MAX ledger. Версия и решение проверяются при постановке,
в worker и под блокировкой настроек непосредственно при фиксации попытки отправки.
Повторные кнопки, webhook и восстановление очереди не создают новый intent.

## Выключение И Выкатка

`VK_BOT_REVIEW_ENABLED=false` запрещает новые подключения, доставку и выполнение
согласованных VK-публикаций. Env читается процессами при запуске, поэтому изменение
требует штатного обновления API-ролей. Блокировка не отменяет уже начатый MAX POST
и не мешает восстановлению ранее подтверждённой квитанции VK-публикации.
По умолчанию возможность доступна, но каждый канал и источник подключаются явно.
Существующие настройки миграция не переключает.

Миграция `20260915120000_add_vk_bot_review` только добавляет nullable/default поля
и новые таблицы. Проверки: `npm run check`, включая SQL/PGlite-тест ограничений,
индекса восстановления и конкурирующих решений. Выкатка: общий API и потребители
контрактов через штатный exact-SHA CI/VPS workflow; Postgres/Redis не пересоздаются.
Live smoke выполняется только на разрешённом тестовом канале из API agent notes.

Отложено: несколько согласующих, принятие в расписание, массовые решения,
настройка источников целиком внутри бота и автоматический перенос неизвестных типов
VK-вложений. Нативный VK video поддерживается существующим bounded upload-путём.
