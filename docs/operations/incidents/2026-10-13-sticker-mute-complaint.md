# Стикеры и очистка после мута — 13 октября 2026

Пользователь сообщил о спаме стикерами в «Поддержка Майор Максимов»: бот выдал
мут, но сообщения остались. Пользователь уточнил: мут был **автоматическим**.
Позже пользователь подтвердил, что остались сообщения **до мута**, и явно
задал новое поведение: **при автоматическом муте удалять сообщения участника
за предыдущие 30 минут**. Это касается текста и всех типов вложений, а не
только серии стикеров. Точное время и message ID жалобы пока не установлены;
название чата само по себе не идентифицирует событие.

## Поведение до исправления

- Автоматическое правило ограничения стикеров удаляет каждый квалифицированный
  стикер. Настроенная лестница выдаёт мут на третьем нарушении; отключение WARN
  не переносит порог мута на первое нарушение.
- После мута новые сообщения того же участника, включая стикеры, получают
  отдельную задачу `MUTE_ACTIVE_DELETE`. Сохранение мута не является DELETE receipt.
- Автоматический мут не запускает ретроспективную очистку всей истории.
  Первый разрешённый стикер до нарушения может остаться по действующей политике.
- Ручной мут использует отдельную очередь и очистку отслеженных сообщений:
  последние 24 часа, максимум 1 000 уникальных сообщений. Запрос не исключает
  стикеры по типу вложения. Pending/failed очистка отлична от установки мута.

Native-регрессия проходит настоящий parser, ingress, PostgreSQL 16, Redis 7,
BullMQ, сохранение санкции и guarded DELETE. Два бота получают копии каждого
стикера. Первый разрешён, три нарушающих удалены, мут сохранён, следующий
стикер удалён с подтверждённым `MUTE_ACTIVE_DELETE`; replay не дублирует DELETE.
Все 107 сценариев набора `webhook-multibot-moderation-guards-fullpath.spec.ts`
прошли. Ответы MAX моделируются; это не доказательство удаления в чате жалобы.
Первоначальное ожидание теста о муте после первого нарушения исправлено после
проверки реального порога; production-лестница не менялась.

## Адресная диагностика и следующий шаг

В окне 14:55:59–15:40:59 UTC прочитаны семь ролей, cap 20 001 не достигнут.
Найдены три `Failed to delete tracked recent message during manual moderation
cleanup` около 15:10–15:12 UTC. Прочие выбранные категории ручной очистки
отсутствуют; это не доказывает полноту выполнения всех задач.

Для трёх ошибок выполнены точные read-only `GET /chats/{id}` через настроенный
MAX endpoint: HTTP 200, название доступно, ни одно не соответствует указанному
чату поддержки. Поэтому эти ошибки не приписываются жалобе. Их исходная причина
не совпала с проверенными категориями и остаётся неклассифицированной;
произвольные сообщения MAX/идентификаторы из журналов в отчёт не выгружались.

## Исправление

`AutomaticMuteCleanup` создаётся вместе с новым применённым автоматическим
мутом в одной транзакции. Это охватывает обычные правила, дубликаты и
обязательные подписки через общий writer, а также durable rule follow-up.
Сохранённые ранее муты автоматически не включаются. У ручной модерации и
участнических жалоб остаются собственные явно заданные механизмы очистки.

- Окно фиксируется относительно `ModerationEvent.createdAt`: от −30 минут
  до времени мута включительно. Проверяются время исходного сообщения и
  exact chat/author/message. Источник кандидатов — сохранённые `message_created`
  receipts, полученные до мута; недоставленные боту сообщения не обнаруживаются.
- Процесс `api-action` читает страницы по 8 receipts через существующий
  `webhook_events_report_history_idx`, сохраняет `(created_at, id)` и держит
  максимум две незавершённые страницы. При перегрузке штатный governor
  откладывает только эту очистку; slow уменьшает страницу до двух receipts.
- Страница продвигается после durable materialization каждого подходящего
  DELETE. Повтор страницы и зеркала от разных ботов используют одинаковые
  ключи причин; потеря Redis wakeup восстанавливается SQL sweep удаления.
- DELETE получает фоновый приоритет. Перед отправкой проверяются точные
  автор/чат/время, текущие права бота и участника, иммунитет, действующий мут,
  отмена санкции, fences и постоянные holds, включая источник самого мута.
- Окно исполнения неизменно: 30 минут после времени мута, дополнительно
  ограничено сроком самой санкции. Ошибки не продлевают ни одно из окон.
  Неизвестный результат DELETE сохраняется как `AMBIGUOUS`.
- `SCANNED` означает завершённую постановку кандидатов, а не успешное удаление.
  Результаты каждой цели остаются в delete intents/attempts. `EXPIRED` и
  `CANCELLED` не считаются очисткой. Публичных служебных сообщений нет.

Аддитивная миграция создаёт только пустую outbox-таблицу и её индексы; существующие
receipts не переписываются. FK связывает время жизни задачи с moderation event.
Новая причина остаётся под `MUTE_ACTIVE_DELETE`: прежний guard отказывает
историческим сообщениям до мута. Откат API поэтому останавливает новую
очистку, а не превращает неизвестное правило в разрешение удаления; таблицу
при откате не удалять. Runtime-only fallback мута при отказе сохранения убран:
новый мут требует durable event вместе с задачей очистки.

## Проверки и выпуск

Первый native проход после реализации: 107 сценариев multibot moderation guards
успешны. Стикерный сценарий теперь проверяет пять DELETE: первый разрешённый
стикер, три нарушения и последующее сообщение во время мута. Дополнительный
проход: 288 тестов, включая native историю, rollback транзакции, возобновление
после сбоя, отмену/истечение мута, администратора, чужого автора, отсутствие
прав бота, неизвестный DELETE и графы production-ролей. MAX HTTP моделируется;
PostgreSQL 16, Redis 7, BullMQ, parser, guards и SQL настоящие.

Расширенный native набор: все 14 сценариев прошли, включая потерю Redis wakeup,
отмену мута/hold во время последней awaited проверки, независимый чат при
зависшей странице, drain при shutdown и обычный PostgreSQL planner на 12 100
receipts с одинаковыми timestamp и глубоким/пустым cursor. Index scan читает
не более восьми строк, без Sort и фильтрации старой истории. Принудительное
отключение sequential scan в итоговой проверке не используется. Ошибка приведения
timestamp в первой версии SQL-фикстуры исправлена; runtime query не менялся.

Общий staged gate сначала остановился на подготовке прежнего ordered-anchor
native-теста: миллионная вставка превысила существующий statement timeout.
Оба одинаковых ordered/frozen fixture теперь создают историю десятью порциями
по 100 000 с проверкой полного миллиона. Лимиты и рабочие SELECT не изменены;
все 14 focused infra-тестов прошли. Staged gate повторяется после этой коррекции.
Exact-SHA CI и production release ещё должны завершиться. Пока новый runtime не объявляется выпущенным.
Для подтверждения исходной жалобы всё ещё нужен точный receipt и remote outcome.

UI-инструмент MAX не инициализируется в текущем WSL checkout
(`sandboxCwd is not a local file URI`). Сообщения, тестовые санкции и диагностические
ответы в пользовательский чат не отправлялись. Старые сообщения вручную не удалялись.
