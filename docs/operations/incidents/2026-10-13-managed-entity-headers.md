# Названия и аватарки управляемых чатов — 13 октября 2026

## Жалоба и подтверждённые наблюдения

Пользователь приложил два скриншота домашнего списка: часть фотографий заменена
инициалами, у нескольких чатов отображается `Chat <id>`. На одной строке фотография
загружается при отсутствующем названии. Это разные поля, и наличие фотографии
не доказывает актуальность всей строки.

В 17:26:17–17:26:22 UTC выполнены адресные read-only `GET /chats/{id}` для шести
ID со второго скриншота через настроенные токены и `platform-api2.max.ru`.
Для всех шести получен HTTP 200 с настоящим названием. У трёх MAX вернул `icon.url`
на `i.oneme.ru`; у остальных трёх изображение отсутствовало в ответе MAX.
Два чата доступны через другой подключённый бот после отказа первого токена.
Это не измерение исторических прав и не доказательство доступности изображений
на устройстве пользователя. Содержимое сообщений и секреты не выгружались.

В 17:34:50 UTC шесть точных ключей кэша заголовков отсутствовали. Ключи списка
конкретного пользователя не исследовались без его точной идентичности.
Отсутствие временного кэша не устанавливает состояние PostgreSQL или прошлую
причину жалобы. Приватные артефакты остаются вне Git.

## Причины и исправление

1. Фоновое чтение обновляло кэш заголовка, а опубликованный пользовательский
   список сохранял прежнюю версию. Ответ `noop` и клиентское сохранение старой
   версии могли оставить `Chat <id>`/пустую фотографию после успешного чтения MAX.
   Теперь при чтении списка локальные заголовки публикуются с новой версией
   через compare-and-set. Обновляются только название, ссылка и изображение
   существующих видимых строк; порядок и назначение ботов сохраняются.
2. Ветка готового diff возвращала ответ до планирования восстановления метаданных.
   Теперь она тоже запускает отложенное обновление; HTTP-ответ не ждёт MAX.
3. Первые восемь чатов без фото считались устаревшими при каждом обновлении и
   могли не пропускать последующие. Общий Redis admission на 120 секунд исключает
   повтор этих же чатов между пользователями и даёт очередь следующим.
4. Чтение только через primary не учитывало активного подключённого помощника.
   Теперь допускается максимум два активных назначения конкретного чата и всего
   восемь запросов MAX за проход, последовательно. Таймаут одного запроса —
   2,5 секунды; 429/таймаут останавливает проход и включает прежний backoff.
5. Пустое/служебное название MAX не перезаписывает уже известное настоящее имя.

Проверка доступа, точная активация ботов и ограничения модулей не меняются.
Обновление метаданных не создаёт новую связь и не восстанавливает удалённую
строку при конфликте версии. Нет `GET /chats`, опроса прав каждого чата при
открытии, тестовых публикаций или изменения пользовательских настроек.
Отсутствующая в MAX фотография продолжает отображаться инициалами.

## Проверки и доставка

422 focused-теста прошли, включая прежние сценарии списка и настоящий Redis 7:
новая версия/patch вместо `noop`, очередь после восьми чатов без фото, переход
на активного помощника, исключение отключённых назначений, остановка при 429,
атомарная конкуренция пользователей и отказ устаревшей записи после удаления
строки. TypeScript, focused ESLint, preflight и refactor guards прошли.

Изменяется только API; миграция не нужна. Полный staged gate, CI точного SHA
и общий API deploy должны завершиться перед объявлением исправления выпущенным.
MAX HTTP в автоматических тестах моделируется; реальные адресные чтения выше
не заменяют проверки списка на устройстве заявителя.

Первый общий gate остановился на прежней тестовой подготовке миллиона строк
одним INSERT за 10 секунд. В эту ветку перенесена та же проверенная коррекция
ordered/frozen fixtures, что и в выпуске автоматической очистки: десять порций
по 100 000, проверка полного миллиона, неизменные timeout и production SELECT.
