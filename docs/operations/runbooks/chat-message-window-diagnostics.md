# Проверка сообщения по чату и минуте

Для жалобы на пропущенное голосовое или другое сообщение сначала установите точный
числовой ID чата и минуту UTC. Пример: 22:33 МСК — 19:33 UTC.

```bash
./infra/scripts/vps-connect.sh postgres-audit chat-message-window -123 2026-10-13T19:33:00Z --explain
./infra/scripts/vps-connect.sh postgres-audit chat-message-window -123 2026-10-13T19:33:00Z
```

Перед чтением отчёта проверьте план: покрытый индекс статуса/времени/ID выбирает
не более 513 квитанций каждого из восьми статусов. Только первые 512 каждого
статуса читаются по первичному ключу, затем фильтруются по чату. При заполнении
sentinel `sample_truncated=true`: отсутствие строки тогда не доказывает отсутствие
входящего события. Отчёт ограничен одной минутой времени **получения** события;
поздняя доставка MAX может попасть в другую минуту.

При усечении минутной выборки добавьте `--slice <0..11>`: каждый slice выбирает
ровно пять секунд той же минуты, с полуоткрытыми границами. Например, slice 6 —
секунды 30–35. Сначала проверьте его plain `--explain`, затем прочитайте все
12 slices последовательно. Только полные, закрытые и успешно полученные slices
вместе покрывают минуту; потерянный или усечённый интервал остаётся пробелом.
`window_seconds`, `from_at` и `until_at` показывают фактическое окно; лимиты строк,
индексы, общий lock и таймауты не меняются.

Отчёт показывает статусы, времена очереди/обработки, ограниченные типы исходных
вложений и фиксированные категории диагностических маркеров. Источник — сохранённый
`normalized_payload.raw`, который читает модерация. Отдельный `raw_payload` обычно
сохраняется лишь в 1% случаев и используется только при отсутствии первого;
`source_basis` показывает выбранный источник. MD5 от строковых
ID сообщения/отправителя позволяет сопоставить результат с адресным MAX GET,
не включая исходные идентификаторы в отчёт. Это диагностическое сопоставление,
а не криптографическое доказательство или разрешение на повторную обработку.
Текст, ссылки на медиа и необработанные ошибки не выводятся; максимум 32 типа
вложений на квитанцию, превышение обозначено отдельным флагом.

Schema v5 сохраняет MD5 исходного текста и отображаемого имени автора для
сопоставления с независимым примером. Имя берётся из `sender.name`, иначе из
соединённых и обрезанных по краям `first_name`/`last_name`. Исходный JSON допускается
несжатым не больше 64 KiB. Для корректного сжатого хранения PostgreSQL 16 применяется
существующая политика `pg16_valid_storage_ratio_v1`: pglz не больше 2880 физических
байт или LZ4 не больше 1028 гарантируют декодированный datum не больше 256 KiB.
Это граница для корректного хранения PostgreSQL, а не проверка повреждённого заголовка.
Другие версии, кодеки и превышения пределов остаются непрочитанными.
`source_hash_storage` и поля политики в отчёте показывают применённую границу;
текст допускается до 8192 байт, имя — до 256 байт.
`source_hash_admission` и отдельные поля `*_hash_admission` сохраняют причину отказа;
непрочитанный источник даёт null, а не отрицательное совпадение.
`plain_max_join_url` описывает только форму текста и не заменяет детектор модерации.
`raw_message_removed_exact` проверяет официальный исходный `message_removed`
для того же чата/сообщения без channel/post identity; это независимое свидетельство
удаления, а не доказательство того, кто удалил или какое правило сработало.

`PROCESSED` не доказывает удаление: в частности, `dormant_observation` означает
только наблюдение неактивным ботом. Отчёт не проверяет текущие/исторические
настройки, иммунитет автора или факт удалённого действия. Для вывода об удалении
нужна независимая подтверждённая квитанция DELETE. Несовпадение с видимым MAX
проверяется по ссылке именно на сообщение; пустая история API не закрывает жалобу.

Команда использует обычный read-only audit role, общий lock, таймауты и проверку
готовности индекса; дополнительных прав БД и произвольного SQL не требуется.

`delete_intent` — точный unique-key lookup по тому же чату/сообщению: статус,
счётчик и времена попыток, исходный deadline, начало dispatch и remote-success.
`reason_sample` читает до 65 причин по индексу intent/reason, отдельно показывает
наличие `VOICE_BLOCKED_DELETE`, `LINK_BLOCKED_DELETE` и превышение предела 64. Сохранённая причина
не заменяет проверку актуальной политики. Null markers не означают успех.

Для задержки повторных попыток используйте отдельный фиксированный каталог:

```bash
./infra/scripts/vps-connect.sh postgres-audit delete-retry-heads --explain
./infra/scripts/vps-connect.sh postgres-audit delete-retry-heads
```

Он читает первые 33 записи каждого из пяти активных статусов по next_attempt_at
и отдельно 33 последних обновлённых AMBIGUOUS, RETRYABLE, WAITING_CAPABILITY,
FAILED_TERMINAL и SUCCEEDED. Вывод ограничен 32 строками каждой из десяти групп
с общим флагом усечения; одна запись может входить в несколько групп. Чтение причин
ограничено 65 на intent. Сохранённая классификация отказа не доказывает текущую
политику или причину всех операций другой когорты. Полные ID,
metadata и raw errors отсутствуют; MD5 intent ID позволяет сопоставить SQL
с отдельным bounded Redis observation. Равные часы на границе дают выборку,
а не стабильную пагинацию. Наличие retry clock не доказывает execution eligibility:
каталог намеренно не повторяет runtime policy и не разрешает replay.

Schema v4 `delete_retry_heads` сохраняет поля v3 и добавляет фиксированные категории
`last_failure_family` для точных сохранённых кодов транспорта, локальной квоты MAX,
circuit breaker, удалённого отказа и PostgreSQL/Prisma. Текст ошибки и префикс кода
не используются для этих новых категорий; неизвестный код остаётся `other`.
`database_statement_canceled` по коду `57014` не отличает timeout от другой отмены.
`database_raw_query_error` по внешнему коду Prisma `P2010` не устанавливает
вложенный SQLSTATE или причину: raw text и `meta.code` не разбираются.
Сохранённый timeout не устанавливает, какой HTTP-запрос выполнялся и произошёл ли
DELETE; для этого нужны независимые invocation-owned transport diagnostics и
dispatch/receipt markers. Старые поля, пределы выборки, индексы и права не меняются.
При отсутствующем обязательном индексе admission завершается ненулевым кодом
до отчёта. Пустой вывод не считается успешной выборкой: в PostgreSQL 16 команда
`\quit 3` игнорирует аргумент exit status, поэтому отказ использует `ON_ERROR_STOP`.

Schema v3 отдельно показывает `remote_success_pair_complete`: сохранены непустой
бот и не будущий timestamp acknowledgement. Один `remote_success_marker` означает
только наличие timestamp. Даже полная пара не заменяет точную проверку отсутствия
для BOT_MESSAGE_AUTO_DELETE. После истечения исходного срока только такая
историческая auto-delete-only проверка может получать интервал не меньше часа;
AMBIGUOUS, исходный deadline и доказательства сохраняются. Смешанные причины
перечитываются под блокировкой строки перед этим решением, чтобы новая обязанность
не наследовала часовую задержку. Каталог не выводит ID бота и не разрешает DELETE.
