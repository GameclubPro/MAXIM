# Надёжность ботов и очередей: проверка 28 сентября 2026

## Подтверждённые проблемы

1. **P0 — запись в Redis остановилась после заполнения системного диска.**
   RDB завершался с `No space left on device`, защита Redis возвращала `MISCONF`.
   Это остановило запись заданий и heartbeat Publisher. После безопасного удаления
   неиспользуемых образов Redis самостоятельно сохранил RDB и возобновил запись.
   См. [отчёт об инциденте](incidents/2026-09-28-publik-redis-disk-full.md).
2. **P1 — приоритет способен бесконечно вытеснять старые RECEIVED.**
   Воспроизведено тестом: старое `chat_title_changed` не допускается в пакет при
   непрерывном потоке более новых `user_added`. Резерв RECEIVED сам по себе не
   гарантировал обслуживание старых событий внутри этого класса. Исправление
   резервирует до четверти пакета для старых backlog receipts, ожидающих не менее
   минуты. Приоритет BullMQ, недоступные предшественники и лимиты нагрузки сохраняются.
   Для пакетов меньше четырёх отдельный резерв не выделяется.
3. **P1 — исключение одного обработчика преждевременно снимает защиту опроса.**
   `Promise.all` завершался на первом отклонении, хотя другие обработчики могли ещё
   работать. Следующий tick получал возможность открыть новый пакет. Ошибки теперь
   изолируются по единице работы; завершение пакета ждёт всех обработчиков. Сбойное
   событие остаётся в БД и сохраняет действующие правила повторной обработки.
4. **P2 — журнал не различал выборку и реальную работу.**
   `selectedCount=100` не означал 100 новых заданий. Добавлены ограниченные по частоте
   счётчики: блокировка предшественником, ожидание подготовки, подготовленные,
   завершённые, ожидающие выполнения, заблокированные при постановке и ошибки.
   `outstanding` включает уже существующее задание и не является числом новых отправок.
   Журнал не содержит текстов сообщений, токенов или идентификаторов участников.
5. **P1 — плановые проверки пользователей вытесняли обновление прав Publisher.**
   Приоритет `stale_user_access` был 5, а `stale_access` — 20. В очереди накопилось
   440 заданий, при этом публикации ожидали `bot_access_expired`. Свежий снимок прав
   самого бота живёт 15 минут и требуется для каждой публикации; плановая проверка
   пользователя обновляет трёхдневный доступ заранее. Исправление ставит обновление
   бота перед плановыми проверками пользователей, сохраняя приоритет ручных команд
   и lifecycle-событий. Ограниченное стартовое обслуживание исправляет приоритеты
   сохранённых заданий; сроки delayed и ключи дедупликации сохраняются. Регрессия
   воспроизведена реальным BullMQ worker на одноразовом локальном Redis.

## Что ещё требует измерения

- После восстановления Redis задержка RECEIVED держалась на уровне десятков минут,
  а QUEUED — единиц событий. Это указывает на этап допуска/подготовки; само по себе
  не доказывает, что увеличение числа moderation workers улучшит ситуацию.
- При перегрузке хоста Publisher откладывает плановую материализацию по governor.
  Снимать этот предохранитель для сокрытия очереди нельзя.
- Фиксированные ограниченные окна oldest/newest могут плохо обслуживать середину
  большого накопления одного чата. Это отдельная гипотеза, а не установленная причина
  текущей задержки. Перед изменением SQL нужен регрессионный сценарий с более чем
  1 000 строками одного чата в degraded и более чем 5 000 в normal.
- Асинхронные фоновые задачи подготовки запускаются через `setImmediate` без общего
  ограничения числа незавершённых задач. Нужен замер их влияния на пул и задержки;
  нельзя просто отбрасывать задачи изменения доступа или владельца исполнения.
- Исторические FAILED/AMBIGUOUS публикации и greetings с dispatch marker не разрешают
  автоматический повтор. Их состояние проверяется по receipt и точному bot scope.
- Размер каталога PostgreSQL определён на уровне файловой системы; конкретные
  таблицы роста не установлены. Хранилищем занимается отдельный оператор. Увеличение
  расходов и удаление данных в этот план исправления очереди не входят.

В 16:06 UTC, ещё до выпуска исправлений, oldest RECEIVED снизился до 396 секунд,
а число RECEIVED в ограниченном отчёте — до 1 752. Это восстановление после
освобождения диска, а не измеренный эффект нового планировщика.

Не требуется смена BullMQ/PostgreSQL, разбиение на новые микросервисы или расширение
инфраструктуры. Крупный рефакторинг выполняется отдельными проверяемыми изменениями
после восстановления обслуживания.

## Проверка выпуска

- Использовать публичные npm wrappers, локальную одноразовую PostgreSQL с миграциями,
  тесты outbox, полный API check и статические проверки по impact plan.
- Сохранить точный bot scope, semantic dedupe, порядок сообщений одного чата,
  timeout quarantine, admission governor и очередь неоднозначных отправок.
- Дождаться `Required` и `Analyze JavaScript and TypeScript` для коммита выпуска.
  При недостатке диска для сборки использовать проверенный CI image preload;
  не снижать минимальный запас диска.
- После deploy проверить все 14 API ролей, Redis, heartbeat Publisher, queue fence,
  динамику задержки в нескольких последовательных окнах и public/closed API smokes.
  Живые публикационные пробы выполнять только при здоровом production и только в
  предусмотренных тестовых сущностях.
- Успешные тесты и heartbeat не являются доказательством доставки всех исторических
  публикаций. Отдельно фиксировать непроверенные и неоднозначные результаты.

- Строгие ingress/admin readiness, public health, OCR sandbox/UDS/Tesseract и

  показывал реальные постановки и завершения, `enqueueBlocked=0`, `workUnitErrors=0`.
- Publisher после выпуска: runtime exact, heartbeat fresh, credentials ready,

  стабилизации; в 16:46:27 UTC подтверждены `normal/healthy`, задержка 0,963 секунды

Отдельные `stale_user_access` задания Publisher в ограниченной проверке всё ещё
завершались ответом MAX «не найдено». Они не дают основания ни выдавать права, ни
отправлять публикации повторно. Для конкретной привязки требуется подтверждение
актуального доступа через штатную проверку Publisher. Накопленные FAILED и AMBIGUOUS
не объявляются доставленными.

Deploy preflight также сообщил, что `POSTGRES_PASSWORD` не задан в production `.env`
и Compose использует совместимый fallback. Перед отдельным обслуживанием самого
PostgreSQL нужно явно сверить конфигурацию с действующим секретом; значение секрета
в документацию не записывается. Это предупреждение не мешало текущему API-выпуску.
