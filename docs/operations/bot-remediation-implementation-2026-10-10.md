## Граница изменения

Единственное изменение планирования — прекращение повторной номинации работы,
которую уже запрещает точное сохранённое состояние подключения Публика.
Оно применяется к фоновой проверке прав и подготовке VK-публикаций.
Сами правила доступа, отправки, санкций, дедлайны и идентичности заданий сохраняются.
Дополнительные изменения касаются диагностики и дискового допуска сборки.

- Планировщик сначала учитывает исходные обязательства доступа, затем исключает
  из enqueue цели с обязательной явной активацией. Курсоры продвигаются по исходной
  странице, включая отказы; обслуживание доступных целей продолжается.
  Проверки прав бота, фонового списка администраторов и пользовательских прав
  используют существующий отказ. Явные Start/forward-подключения остаются в своих
  прежних обработчиках. Метрика `activationRequiredRows` показывает исключённые
  номинации, не превращая их в успешные обновления.
- VK перед обработкой пакета читает точную сохранённую привязку один раз.
  Подтверждённый запрет прекращает повторные проверки отдельных кандидатов.
  Новый типизированный отказ точного чата до отправки останавливает только текущий
  пакет. Кандидаты сохраняют NEW, исходную отметку ожидающего автопостинга и право
  на штатное восстановление; импорт источника и другие цели продолжают работать.
  Новое разрешение всё равно проходит readiness и финальную проверку перед отправкой.
- Диагностика VK выполняет секции последовательно и возвращает название неудавшегося
  этапа с разрешённой категорией Prisma/SQLSTATE. Один P2010 остаётся
  `unclassified_sql_error`; SQLSTATE 57014 означает отмену запроса, а не доказанную
  причину отмены. Сырые SQL, параметры и ошибки не выводятся в аварийном завершении.
- Ошибки проверки сообщения опроса получили отдельные stage/outcome и ограниченную
  категорию причины. Произвольный 404 остаётся неопределённостью; опрос и голоса
  сохраняются. Повторная публикация не добавляется.
- `postgres-audit queue --explain` планирует только фиксированный запрос, с прежней
  ролью и лимитами. Выборка и oldest lookup используют точный индекс
  `(status, created_at, id)` и стабильный порядок при одинаковом времени. Порог сборки общего API приведён к 20 GiB; static остаётся
  6 GiB, отдельная подготовка multibot — 10 GiB.

Миграций схемы, новых очередей и изменений concurrency нет. Существующие SQL/Redis
записи сохраняются, поэтому возврат к исходному совместимому runtime не требует
отката данных. Предыдущий runtime снова начнёт лишние номинации, но не получит
дополнительных полномочий.

## Проверки и выпуск

Локальные focused-проверки: refresh — 187 passed с PostgreSQL; VK и диагностика —
257 passed, один native skip в запуске без stores; ограниченный каталог — девять
passed с PostgreSQL; дисковые границы — 19 passed. Финальная широкая проверка
и проверка staged-снимка выполняются перед commit/push.

Первый широкий запуск пересёкся с отменой экспериментального уменьшения SQL-выборки
и получил три несогласованных ожидания в queue-тестах. Его результат не используется
как проверка финального дерева. После отмены эксперимента запущена чистая проверка.

Операторские агрегаты и журналы проверок сохраняются вне Git; сырые сообщения,
токены, идентификаторы людей/чатов и дампы в этот отчёт не включаются.

Чистый широкий прогон прошёл static (2 709 passed, два условных skip), infra
(2 589 passed, без skip), contracts и API typecheck. API выполнил 21 086 тестов
успешно; два теста GROUP-retention обнаружили предположение о пустой общей таблице,
один отдельный commercial-native тест пропущен. Неизменяемый receipt из предыдущей
suite сохранялся правильно; неверным был ожидаемый общий счётчик scanned.
Тесты теперь сами создают постороннюю закреплённую запись, учитывают существующий
ограниченный фон и требуют неизменности всех таких записей после очистки.
Production retention не менялся.
