# Публик: форматирование и подписи — 13 октября 2026

Пользователь описал редактор в MAX Desktop 26.35.1 на Windows 11 Pro:
повторное нажатие B не снимает жирное начертание, поэтому приходится удалять
и переписывать блок. Отдельно уточнено, что подпись отсутствует при ручной
публикации в канале MAX. Это два разных пути обработки.

## Воспроизведённый дефект редактора

`MaxRichTextEditor` всегда оборачивал выделение в новый элемент; обратной
операции не было. При пустом выделении он вставлял слово-заготовку. Состояние
панели `BroadcastContentComposer` не получало активные стили редактора.
Браузерная регрессия на исходном коде подтверждает, что после повторного B
выделенное слово остаётся жирным, независимо от похожей строки Markdown.

Для B/I/U/S используются нативные команды редактирования: они снимают стиль
с выделения либо переключают стиль будущего ввода, сохраняя выделение и историю
отмены. Состояние кнопки следует текущему выделению и режиму ввода; добавлены
`aria-pressed` и видимое активное оформление. Декоративная жирность/подчёркивание
ссылки больше не подменяет семантическое состояние этих команд. Ссылки остаются
визуально обозначенными и проходят прежний безопасный URL parser.

Общие стили панели перенесены из лениво загружаемого `broadcast-studio.css`
в CSS самого composer. Прямое открытие `/publications` больше не зависит
от посещения старого экрана. Это перенос владения компонентом, без новых
зависимостей, формата хранения, API или расширения допустимой разметки.

Нативный `execCommand` устарел как веб-стандарт, но здесь выбран для ограниченного
набора поддерживаемых команд с браузерной историей отмены. Ручная замена DOM
не сохраняет такую историю и состояние будущего ввода. Команды кода, заголовка
и диалог ссылок остаются отдельными операциями; этот фикс не является заменой
редактора полноценной библиотекой документов.

## Проверки редактора и выпуск

Браузерный тест использует настоящий composer, стили Publisher и сериализованный
черновик. Проверяются частичное/полное снятие каждого из четырёх стилей,
смешанное выделение, вложенный курсив, сохранность ссылок, ввод после переключения,
Ctrl+B, undo/redo, повторное открытие и `aria-pressed`. Исходная реализация
падает на фактическом состоянии выделения; исправленная проходит desktop,
iPhone и Android размеры, каждый в светлой и тёмной теме, с mouse/touch вводом.
Новая регрессия включена в обязательную Mini App CI lane.

Это Chromium с эмуляцией размеров/сенсорного ввода, не запуск внутри указанной
версии Windows MAX и не проверка iOS/Android WebView на устройствах. Windows
computer-use недоступен из-за ошибки инициализации
`sandboxCwd is not a local file URI: file:///home/yourname/projects/MAXIM`.
Гифка в доступных вложениях отсутствует; дефект воспроизведён по описанию.

Выпуск: staged impact checks, production bundle budgets, exact-SHA CI,
деплой только `miniapp-major-static` и smoke канонического `/app/`.
Подготовленное отдельно API-исправление счётчика комментариев сохраняет свой
shared API scope. Подписи в этой правке покрываются только тестами.

## Ручная публикация и подпись

Добавлены два сценария полного пути с реальными PostgreSQL 16/Redis 7:
ручной пост администратора с фото, с sender и без sender. Настройки читаются
из БД, используется настоящий `ChannelPostSignatureService`, ingress,
очереди, авторизация, блокировка EDIT и durable marker. Две копии webhook
от разных ботов приводят ровно к одному EDIT; фото сохраняется, подпись верна,
marker `SUCCEEDED`, повторная обработка не редактирует пост вновь.
Все 106 сценариев этого native-набора прошли. MAX HTTP моделируется.

Readonly окно журналов 13:41:29–14:11:29 UTC охватило семь ролей, без усечения
cap 20 001 строк на роль. Не найдено пяти выбранных категорий ошибок подписи,
сканирования и редактирования. Отсутствие этих сообщений не является квитанцией
подписи для каждого поста: успешные EDIT в этом отчёте не сопоставлялись с каналами.

В уже выпущенном коде подпись обычного поста готовится по свежему MAX snapshot
внутри общей блокировки редактирования. Signature-only каналы включены в scan
и recovery. Ручной direct-пост без sender допустим; замена анонимного forward
не разрешена. Настройка при включении проверяет edit-права. Publisher сам
не дописывает Major text signature: это существующая граница профилей;
подключённый Major отдельно обрабатывает новый пост канала.

Для конкретной жалобы запрошен канал и пост. Следующий шаг — проверить текущую
настройку/права, поступление `message_created`, marker и результат EDIT через
ограниченную адресную диагностику. Нельзя без квитанций обвинять другого бота,
считать native fixture доказательством исправления этой жалобы, массово
переписывать старые посты или повторять операции с неизвестным исходом.
