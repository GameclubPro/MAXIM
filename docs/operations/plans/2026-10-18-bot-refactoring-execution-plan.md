## Порядок с максимальным ожидаемым выигрышем

2A0, 5P и Callback 3 выпущены. Оставшаяся очередь реализации: **завершить 4 → 2A → 5A → 5B → 5C → 6 → 7**, выделяя типизированные компоненты этапа8 по мере изменения доказанных границ. Активен один implementation/release-этап; номера сохранены для связи с каноническим планом. После 2A можно разрабатывать и проверять выключенные совместимые пути5A–5C, не дожидаясь2D. До первой реальной экспозиции ускоряющего пути выделить отдельные последовательные выпуски минимальной цепочки **2B/2C-DELETE и 2D-Публик**, затем закрыть назначенную живую приёмку. Только после этого допустимы5%/25%/100%. Это обязательный слот перед расширением, а не запрет безопасной разработки off-path.

2A уточняет существующую диагностику;2B/2C и2D добавляют только недостающие совместимые связи и полный знаменатель на основе действующих журналов. Универсальная новая observability-платформа не требуется. Скорость только завершённых операций остаётся отдельной метрикой и не заменяет закрытые когорты всех принятых операций.

### 2A0. Завершённый выпуск совместимости

Распознаваемый режим `test` отклоняет shortcut **до SQL** и выполняет полный действующий rollup. Четыре недоказанных SQL-кандидата отвергнуты; исходные физические бюджеты и таймауты не ослабляются. Numeric SQL сохраняется, но его включение не разрешается фактом локального теста.

Нативный prerequisite: один owned fixture сохраняет непрерывный insert/delete цикл на 50k и четыре состояния истории, каждое с retained/empty/one cases. Подготовка, вставка, удаление и proofs разделены на конечные последовательные тестовые фазы. Остановка запрещает следующий SQL, а teardown сначала дожидается принятой операции и только затем очищает свои строки. Проверка gate/drain моделирует асинхронную операцию; это не доказательство реальной SQL race. Сохранены 30s Jest, 10s SQL, 15s proof transaction и 45s cleanup. Latency query/index assertions не изменены; они прошли после полного churn на той же disposable базе. Отдельно прошли filtered lifecycle и все семь latency cases на свежих stores: 8 passed, 95 остальных assertions намеренно исключены фильтром; cleanup завершён. Точный CI исправленной ревизии и merge успешен; предыдущий failed CI сохранён как историческое доказательство.

В coalesced warning добавляются только уже вычисленный `isCritical` и доказанный `failureOrigin=local_quota`; остальное остаётся `unlinked/unknown`. Новых await, транспортной корреляции, retry и изменений health/лимитов нет. Выполнены точные CI, штатный API-only deploy `9938017b`, strict smokes, независимая сверка манифеста/образа/неизменных statics и stores, flags и normal/healthy после штатного окна стабилизации. **Exposure shortcut в test остаётся нулевым; performance не принят.**

### 5P. Уменьшить payload действующих чтений

Точный scope: **два envelope-select по 4 поля, один delivery-select финализатора по 15 полей**, planner `Pick<sentCount | cycleCount>` и точные inferred-типы callbacks без `any`. Сохранить полные rowsets, predicates, расположение/число запросов, текущий порядок массивов, CAS/lease/deadline/SEND/receipt/unknown и repair reload. Убрать неиспользуемые dialog/post-action JSON. Типы — Prisma select/GetPayload и точные Pick; select-aware doubles возвращают только реально выбранные поля. Миграция, runtime toggle и новый memory framework не нужны.

Сначала focused callers: оба envelope fallback, missing/current-status/occurrence-clamp/nextSendAt/canRetry; finalizer/verification/cancellation, legacy all-null и положительное verification enrollment, pending/quarantine wake, mixed terminal, lost lease/CAS. Успешный NOW не доказывает исполнение fallback-чтений. Добавить небольшие реальные PostgreSQL caller/lease-CAS проверки; прямое равенство reader не заменяет race coverage.

**Native equivalence:** full и реальные projected Prisma reads в одном RepeatableRead snapshot на **64/10k/50k**. Проверить значения, число строк, точную идентичность и исходную последовательность targets без добавления ORDER BY или сортировки сравнения. Реальный SQL отличается только проекцией. В ready fixtures использовать принимаемый действующим parser контекст с 8-KiB сжимаемым padding под фактическим cap 64KiB; измерить pg_column_compression, stored/logical sizes и сообщить наблюдавшийся inline/compressed/external охват, не предполагать TOAST. Большие readpairs выполнить один раз на тех же ready fixtures после timed samples/postconditions и reset вне timing, не создавать вторую большую матрицу.

**Размер результата:** вне всех timed intervals посчитать точный `serializedPrismaResultUtf8Bytes` — UTF-8 длину документированной **row-wise JSON-сериализации реальных полных и projected Prisma результатов**, с одинаковой null/date encoding. Сохранить scalar rows/keys/digest, освободить proof-объекты до следующей ячейки. Это application JSON bytes этих чтений, **не PostgreSQL wire bytes, allocation bytes или размер heap**. Длина конкретного D-массива не измеряет hydration всего turn: **`hydratedDeliveryCount=null` остаётся unknown**.

**Парный runtime-профиль:** одинаковые frozen tooling/payload/order на выпущенном 2A0 baseline и 5P candidate; rollup и temporal selection off. Только **5 cells: ready NOW 64/10k/50k, verification NOW64, deadline64**; один warmup + три measured вызова = **20 calls/arm**. Сохранить семь малых authorization/cancellation/verification controls. Сравнить реальные outcomes, writes/affected rows, исходную action/target sequence по immutable fixture ordinal и receipt linkage. Без повторного full24cell/maintenance/targeted, fresh-Node children, forced GC/`--expose-gc`, heap snapshots, allocation profiler, GC hooks или Prisma proxies. Opt-in `--projection` реализован; CLI-проверки 6/6 прошли.

Существующие elapsed/Node CPU, process memory snapshots, sampled RSS/GC/event-loop дают только наблюдавшиеся локальные величины с coverage/gaps. Порядок диагностических readpairs одинаков для двух arms: они влияют на cache/память следующей ячейки. Нет whole-turn hydration/allocations, exact retained heap/peak или leak claims. Пропущенная ячейка/native skip/timeout/teardown gap оставляет приёмку открытой; outliers не удалять. Достаточный результат 5P — те же строки/решения/действия, меньший selected/serialized payload и честно записанные локальные наблюдения. 5P остаётся O(N); CPU/RSS improvement фиксируется только если наблюдается, production p95/p99 или проценты ускорения отсюда не следуют.

**Локальный срез 18.10, 12:12 UTC:** оба парных прогона завершены exit 0 с одинаковыми tooling и неизменными исходниками до/после. В каждом — 20 public calls, семь controls и три native readpairs. ### 3. Передавать точный чат в VK callback ACK

Исправленный в выбранном main source gap: `VkBotReviewService.answer()` прежде передавал bot/source без `rateLimitEntityId`. MAX-клиент использовал общий `unknown-target:bot` answer scope, и разные личные диалоги конкурировали в одном fallback. Это подтверждает устройство лимитера, не величину production-задержки.

В выбранном main передаётся сохранённый в job **privateChatId** с прежними bot/source, формулами и ключами лимитов. Не выводить адресат из user/callback ID. Публичный `process` проверяет успех, бизнес-отказ, повторный ACK и отсутствующий чат. Две обработки одного согласования дают два допустимых ACK, но одно действие публикации; отказ ACK не отменяет сохранённое решение. Missing chat не приводит к ACK или выдуманному scope.

Проверены десять прямых callback callsites: известный target теряется только в VK. Это исправление не устраняет общий лимит бота. Нынешние class/service caps и приоритеты не гарантируют выделенную общую квоту или отсутствие голодания. Перед изменением admission нужны точные когорты отказов/ожиданий по bot/class при смешанной нагрузке; общий лимит, deadline и один владелец retry сохраняются.

### 4. Дожидаться полной операции восстановления комментариев

В установленном main `78a68b25` recovery при shutdown только очищает таймеры; первый scheduled pause-check находится вне `inFlight`. В текущем Shutdown 4 этот разрыв закрыт через `RuntimeWorkerOwner` и учёт полной принятой операции. Локально прошли 57/57 focused cases, включая 19 actual Nest lifecycle-сценариев, typecheck и refactor guards. Staged broad прошёл: 19 976 API-тестов без падений, 2 731 пропуск сохранён; сборка, static и docs успешны. Точный CI, выпуск и production-приёмка остаются отдельными gates.

Синхронно закрыть admission/таймеры; отслеживать всю принятую операцию от pause-check через coordinator до завершения. В штатном runtime shutdown стабильный worker adapter ждёт её до context.close, пока SQL/Redis доступны. При истечении grace force завершает teardown без нового ожидания и без объявления бизнес-операции успешной; direct Nest close не доказывает порядок остановки провайдеров. Сохранить **5s grace / 9s hard watchdog**. Force close не должен снова ждать бесконечно при module destroy; повторное закрытие идемпотентно.

Проверить shutdown во время первого pause-check, ожидания coordinator и batch; ошибки, повторный close и force. Сохранить существующие coalescing, повторную проверку operator pause, batch=50 и правила marker/authority. Этот этап не восстанавливает потерянный job/контекст и не разрешает unknown SEND.

Текущий единственный runtime-этап — завершение проверок и выпуска Shutdown 4; следующий — 2A. Диагностический разбор OCR и проектирование 5A не открывают параллельный выпуск. Новый подтверждённый production-инцидент может изменить приоритет.

### 2A. Установить точную связь отказа с вызовом HTTP

Расширить только существующую ограниченную диагностику: явный типизированный контекст одного вызова, фактические method/endpoint из конечной конфигурации и фаза отказа. Preflight GET не становится DELETE из-за sourceTag; transport ACK и подтверждённый предметный результат различаются. Неподдержанные пути остаются unlinked. Сохранить публичные значения/ошибки, порядок awaits, счётчики и лимитирование; между final guard и адаптером нет новой асинхронной работы. Переиспользованный Error, ambient lastRequest и Axios config из ошибки не доказывают происхождение.

**Доказательство:** реальные public callsites, concurrent/nested calls, повторно используемый frozen Error, успешный HTTP с последующим локальным отказом, override method/url, 2xx без предметного ACK. Отказ диагностики не влияет на действие. Это связь отдельного coalesced warning, не полный знаменатель и не durable receipt chain; последнее принадлежит 2B–2D.

Отдельно воспроизвести source-level несовпадение `ledger.recordFailed` и watchdog: сохранённый `max_member_pre_dispatch_guard_rejected` может скрывать исходный quota/circuit refusal. Нужна регрессия через настоящую typed quota-ошибку и настоящий ledger. Нельзя разрешать retry для всего этого кода: им также представлены истёкшие или отозванные полномочия, а исходный guard не сериализуется. До положительного доказательства безопасного no-effect и повторной авторизации поведение остаётся fail closed.

### 5A–5C. Ограничить повторный рабочий проход порцией

Это основной следующий архитектурный резерв CPU, памяти и latency. Разделить на три выпуска с самостоятельными gates.

- **5A — совместимые readers и инвалидирование.** Добавочные nullable version/seal, producers/readers off. До DDL доказать общий порядок реальных блокировок и охват writers, repair, FK CASCADE/SET NULL. Простой child-trigger с parent UPDATE не принимается без native proof. Проверенные пути content-edit/retry/fresh-materialization/deadline/stopped-cleanup берут общий publication-calendar; это не гарантия охвата всех writers. Противоположные порядки строк дают потенциальный граф, но сами не доказывают достижимый deadlock. Native race сохраняет реальные advisory locks, полные CAS-предикаты и границы транзакций. Append-only invalidation — кандидат, не выбранное решение. Проверить первый seal, visibility после FK wait, свежий SQL после ожидавшего CAS, races с обоими победителями и off/WAL cost. Не переписывать parent на каждую delivery/lease. Этот reader-compatible выпуск задаёт rollback floor.
- **5B — выдача сертификата новым полным снимкам.** Только атомарно доказанная новая материализация получает уникальный seal token и версию. `existing > 0`, отсутствие envelopes и старая частичная история не доказывают полноту; повторно использованный occurrence не получает новую authority из догадки. Все структурные изменения инвалидируют доказательство. Сохранённая после ACK квитанция не зависит от пригодности seal.
- **5C — bounded automatic ongoing turn.** Вход до полной загрузки targets/envelope JSON. Проверка поддерживаемой версии и текущего token внутри сериализованного claim и progress CAS. Изменившийся token запрещает продолжение. Пустой SKIP LOCKED не разрешает finalize, сертификат состава не доказывает settlement, SQL error не становится empty/success. Manual/repair/recovery/global terminal finish сохраняют полный путь. После SEND/ACK fallback допускает только settlement/recovery, без повторного SEND. Не вызывать O(N) finalizer после каждой непустой порции без отдельного доказательства необходимости.

До выбора DDL провести конечную native проверку кандидата5A: genesis/no-reseal и полный охват writers/FK; изменение после seal в той же транзакции; CACHE>1 и commit в обратном порядке; rollback/savepoint строк; реальное ожидание блокировки и отдельный свежий READ COMMITTED snapshot; оба победителя races и точный PostgreSQL/Prisma transport. Sequence не задаёт commit order, waited CAS не обновляет общий snapshot, следующий SELECT не сериализует будущих writers. При недоказанной полноте оставить полный путь и не расширять migration/framework. Полные технические условия сохранены ниже в разделе «Невыбранный кандидат5A»; append-only/fullXID остаётся кандидатом.

Сохранить SEND quantum=4, verification budget=50 и final authorization непосредственно перед внешним действием. Внутренний progress не подменяет полные публичные массивы targeted callers.

**Доказательство:** 10k/50k, retained history/skew/stale statistics, locked rows и races revoke/stop/edit/cancel; plans rows×loops, heap fetches/buffers, память/event loop и полная парная runtime-матрица. Малый LIMIT/output не доказывает малое физическое чтение. Первичная материализация, массовая отмена и terminal settlement имеют отдельные бюджеты; bounded turn не обещает постоянной стоимости всей публикации.

### 6. Выбирать готовые задачи по транзакционной readiness-проекции

После bounded turn добавить versioned hints: SEND, receipt verification, blocker recheck, lease expiry и исходный deadline. Каждый writer атомарно обновляет или инвалидирует hint. Это ускоряет поиск; журналы и fresh authorization остаются источником истины и права на SEND.

Сначала сравнить чистые решения старого/нового selector без второго claim или эффекта, затем включать индексную выборку. Отдельно ввести fairness **3 порции ready / 1 recovery**; внутри recovery чередовать receipts и наступившие blocker checks. Свободный бюджет отдавать доступному классу; равные сроки имеют стабильный порядок. Сохранить nextAttemptAt/lease/deadline, одного владельца retry и общий бюджет между workers.

**Доказательство:** старые blockers перед свежей готовой работой, постоянный NOW с расписанием/recovery, contention/WAL, late receipt и потеря Redis после SQL commit; отсутствие голодания и дублей. Не повышать квоты/concurrency, чтобы скрыть дорогие чтения.

### 7. Сохранять durable продолжение комментария

Минимальные version/phase и ссылки на immutable данные записывать атомарно с SQL marker. Outbox relay может дублировать; исполнитель проверяет фазу, ownership, настройки и квитанцию. Известная квитанция завершается без SEND; unknown остаётся под fence, старая история без доказанного контекста — на проверке.

**Доказательство:** добавочная миграция и совместимые readers/rollback floor; SQL commit без Redis job, двойной relay, конкурентные executors, crash до/после MAX ACK и записи receipt, отзыв прав/отмена. BullMQ job ID не гарантирует exactly-once MAX SEND.

### 8. Выделять компоненты вокруг доказанных контрактов

Порядок: Публик selection/preparation/send/settlement → модерация lifecycle/commands/group messages/channel posts → MAX transport/admission/outcomes. Публичные фасады и обязательные зависимости сохраняются; новые границы типизированы. Неполные события и nullable MAX payload закрепить fixtures. Сравнивать чистые решения; внешнее действие исполняет один путь.

Ранний webhook ACK после DELETE-намерения требует отдельного доказательства порядка страйков/санкций и в этот цикл не входит. Перенос монолита, смена брокера или SDK сами по себе не являются доказанным ускорением.

## Выпуск и критерии остановки

Каждый этап фиксируется отдельно: **написано → локально проверено → точный CI → развёрнуто → принято в production**. Affected native/unit и публичные checks выполняются до дорогого broad; повтор broad — при изменённых входах, отказе или новом gap. Требуются успешные **Required и Analyze JavaScript and TypeScript точного target SHA**.

Штатный guarded deploy: свежий baseline → точные зелёные push-main images → синхронизированный VPS SHA → strict smokes/census/immutable component manifest. API-образ обслуживает все 14 ролей и оба native auxiliaries: обновить весь выбранный компонент; unaffected statics наследуют точные baseline source/ref/image. PostgreSQL/Redis не пересоздавать; сохранить очереди, deploy lock, disk floors и соседние проекты. Preload не равен deploy; удалённый `deploy main --plan` не является read-only preflight.

Живая приёмка — в уже разрешённой сессии Публика, только назначенные test chat/channel, со свежей проверкой точного типа и прав бота/человека, маркированным контентом. Повторного разрешения на эту сессию не нужно. Недоступная browser automation оставляет gate открытым; MAX ACK не доказывает видимость в клиенте.

После 2D и test-приёмки: **5% ≥24h → 25% ≥24h → 100% ≥48h**, стабильные группы сущностей. Для каждой ступени нужны ненулевая реальная экспозиция, закрытые когорты всех принятых операций и сравнимая нагрузка. Недостаточная выборка, receipt/retention gaps или пропуски наблюдений означают незавершённую приёмку.

Стоп: новый дубль внешнего действия, неверная санкция, обход прав, потеря квитанции либо ухудшение p95/p99 >10% при сравнимой нагрузке. Сначала безопасно выключить новый путь с проверкой фактических flags; image rollback не меняет dotenv и не доказывает off. Соблюдать rollback reader floor, сохранить deadlines/journals/fences. Unknown не повторять. Очистка очередей, снятие fences или destructive recovery не являются способом добиться зелёного статуса.

Инфраструктура, интеграция MAX и конечный пользовательский результат принимаются отдельно. Старые ordered/quarantine кандидаты требуют ограниченного точного evidence, а не replay; OCR — минимальных monotonic timing/exit facts без повышения timeout/concurrency. Эти диагностические ветки не вытесняют основной этап без доказанного инцидента. Для повторного readiness-инцидента нужен bounded reason-vector одного и того же head: lease/start, SQL repair retry и актуальность доказательства ожидания. Раздельные SQL-чтения и кэши ingress/admin могут давать разные наблюдения, но это не установленная причина конкретного 503. Не ослаблять readiness/fences; SQL repair schedule не выдавать за BullMQ retry.

Production OCR вызывает runNativeTesseract напрямую. operationElapsedMs включает native input/child scheduling/recognition и проверку завершения process group, но не recycle/readiness; queueWaitMs округлён и начинается после полного валидного frame. Разность requested/budget не измеряет IPC. Native CPU на изображение при UDS не измерен, scheduled wait — назначенный delay, не фактическое ожидание. Эти популяции и percentiles не суммировать; timeout/restart фиксируют срабатывание пути containment, но не первопричину, OOM или восстановление.

### Невыбранный кандидат5A

Технические условия ниже сохраняют полную матрицу проверок кандидата. Это не выбранная DDL и не разрешение на включение нового пути.

До выбора DDL доказать genesis/no-reseal и полный охват writers/FK. Удаление envelope, на который ссылается P.legacyBroadcastId, уже вызывает SET NULL; новый parent-edge проверять отдельно на втором envelope без этой ссылки. UNIQUE(occurrence,xid)+DO NOTHING скрывает пост-seal изменение в той же транзакции: нужен отдельный сохраняемый event выше собственного cutoff, взятого через nextval того же backend. Проверить атомарный rollback изменений и events, а также rollback до/после seal; использованные sequence-значения не откатываются. Для доказанно первой материализации конкретного occurrence видимый структурный event этого occurrence с другим top-level fullXID отзывает seal независимо от sequence. Это не правило для всей исторической ленты: чужие scope исключаются по доказанной принадлежности, а старая/повторная материализация и недоказанный genesis остаются на полном пути; старые события того же occurrence с другим XID нельзя отбрасывать только по sequence. При CACHE>1 воспроизвести резервирование младшего кеша backend B, commit полной материализации/seal backend A и затем изменение B уже видимой delivery. После реального lock wait нужен отдельный свежий SQL snapshot. Это кандидат для доказательства, не выбранная реализация.
