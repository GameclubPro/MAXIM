# Надёжность Публика и модерации: аудит и план — 13 октября 2026

Статус: реализация и выпуск в работе. Исходные результаты аудита ниже сохранены как историческое свидетельство; они не являются проверкой нового выпуска.
Это продолжение проверки после выпуска сохранённого каталога чатов и проверки
прав при открытии выбранных настроек. Возвращать массовый опрос прав нельзя.

## Что установлено

1. **Подписка может сама выключиться при сохранении настроек из-за временной
   ошибки MAX.** Валидатор удаляет любой непроверенный источник, включая 503;
   при пустом результате выключает ограничение. Это воспроизведённый дефект.
2. **Добавление неизвестного каталогу канала по публичной ссылке проверяет только
   один токен.** Отказ текущему/основному боту обрывает поиск до проверки другого
   модератора, который может быть администратором канала. Воспроизведено локально;
   конкретная пользовательская жалоба без ссылки и времени ещё не атрибутирована.
3. **Публик сознательно прекращает никогда не начатые отправки после пяти минут
   просрочки.** Это действующая политика, несовместимая с новым ожиданием
   «не пропускать из-за временного сбоя». Менять её нужно явно, сохраняя защиту
   от повторов отправки с неизвестным исходом.
4. **Точный таймер Публика не обеспечивает изоляцию от фоновой работы.** Он ждёт
   общего координатора, где операции восстановления могут последовательно
   обрабатывать десятки записей. Приоритет влияет на следующую работу, но не
   прерывает уже выполняющуюся. Воспроизведено локально.
5. **Одна неготовая цель блокирует начальную подготовку всей публикации.**
   Локальный сценарий со 100 целями, из которых 99 готовы, не начал подготовку
   ни одной из них из-за отказа в сотой. В сочетании с пятиминутным окном это
   создаёт риск пропуска отправки в исправные каналы.
6. **Закрытие группы и уведомление — разные операции.** Закрытие реализовано
   удалением сообщений обычных участников. Нативного запрета набора/отправки
   сообщений средствами MAX здесь нет. Без своевременных webhook и удаления
   сообщения могут оставаться видимыми, даже если режим включён.
7. Есть свежие ошибки подписки, опросов, антидублей и действий модерации.
   Успешные тесты, пустая очередь и HTTP 200 не доказывают исправность каждого
   модуля в каждом чате.

## Подтверждённые дефекты и архитектурные ограничения

### S1 — потеря конфигурации подписки при временной ошибке, P0

Код: `apps/api/src/admin/admin-required-subscription-runtime.ts`,
`assertRequiredSubscriptionSettings`, строки 695–736. Catch не различает
явный отказ MAX и 429/503/тайм-аут/ошибку сохранения proof. Любой отказ превращается
в удаление цели; пустой массив выключает подписку. Обычный save вызывает
валидатор без проверки, менялись ли поля подписки:
`admin-chat-settings.ts:1046`. Следовательно, сохранение другой настройки также
может изменить уже работавшую подписку. Bulk apply валидирует при переносе
всех настроек либо полей подписки.

Локальный сценарий: один выбранный источник, проверка возвращает временную ошибку;
результат — `enabled=false`, `targetCount=0`, исходный массив имел одну цель.
Существующие тесты намеренно закрепляют удаление непроверяемых целей, но не
проверяют сохранность конфигурации при временной ошибке.

Исправление:

- Хранить выбор администратора независимо от текущей доступности цели.
- Для неизменённой подписки обычный save не должен делать remote-проверки целей.
- Для нового источника проверять только его. Не удалось проверить — не фиксировать
  его как подтверждённый и не удалять остальные; вернуть конкретную ошибку/статус.
- Явный отказ прав хранить для точной пары bot/target и capability; цель остаётся
  видна с причиной и действием восстановления. Временный отказ не меняет роль бота.
- Обновления настроек — с revision/CAS; запоздалый ответ проверки не переписывает
  новый выбор. Не включать уведомление автоматически, если пользователь его выключил.

Приёмка: 429/503/timeout/Prisma error на одной или всех целях не меняют сохранённые
IDs/enabled; unrelated save делает 0 target GET; частичный bulk apply не очищает
другие цели; свежий explicit denial влияет только на нужный bot/target.

### S2 — поиск канала и неоднозначное отображение, P1

Код: `admin-required-subscription-runtime.ts:88,199,236,401`,
`max-client.service.ts:3273,8573`,
`apps/miniapp/src/pages/settings-required-subscription-state.ts:37`.

При промахе каталога `getChannelSnapshotByLink` вызывается без `botId`.
`resolveBot` выбирает текущего или default; отказ немедленно превращается в
«не найден». Перебор кандидатов существует только **после получения chatId**.
Локальный mock: default получает 403, peer-b мог бы вернуть канал; выполнен
один запрос, результат 400, peer-b не вызван.

Отдельно headers для settings повторно проверяют все выбранные цели и фильтруют
любую ошибку. Если цели нет также в личном каталоге пользователя, UI пишет
«Недоступный источник / Ссылка недоступна». Это неверное объяснение для 503
или временно недоступных метаданных. Сохранённые IDs сами по себе этот GET не удаляет;
их удаление происходит в S1 при save.

Исправление: сначала сохранённые метаданные и bot/target proof, затем по запросу
администратора ограниченный lookup одной ссылки через подходящих модераторов.
Известный бот цели первым; при неизвестном ID — максимум число активных
модераторов, не список их чатов. Concurrency 1–2, общий deadline, single-flight
по нормализованной ссылке, отрицательный cache отдельно по bot и виду отказа.
Токен Публика не использовать для модерации. По успешному ID сохранять bot affinity
и перечень доказанных кандидатов. Окончательный «нет доступа» допустим после
терминальных результатов всех кандидатов; смешанный timeout/denial — unknown.

UI показывает сохранённое имя/ID сразу и отдельные состояния: подтверждён,
проверяется, MAX временно недоступен, требуется восстановить права. Чтение экрана
не зависит от скорости всех target GET. Чужие каталоги/состав администраторов
не раскрываются; право изменять исходную группу проверяется отдельно.

### S3 — слишком широкое распознавание потери доступа, P1

`max-membership-lookup.service.ts:2365` считает любой 403/404 терминальным,
а codeless 404 преобразует в `chat.not.found`. Этот результат передаётся в
`recordBotAccessProbe`; lookup issue/backoff действует на chat/policy. Это
подтверждённая широта классификации, но конкретный ложный отзыв прав в production
этим аудитом не доказан.

Нужна единая типизированная классификация: подтверждённый отзыв роли, отсутствие
конкретного участника, недоступный endpoint/чат, временная ошибка, неизвестно.
Один GET membership не должен приравниваться к доказанной потере всех capability.
При явном отказе одному боту сначала использовать другой уже подтверждённый
маршрут цели; backoff не должен запрещать здорового peer. Никаких санкций по
unknown; устаревшее отрицательное membership перед удалением подтверждать заново.

### S4 — подтверждение роли смешано с активацией подключения, P1

`assertBotCanInspectRequiredSubscriptionChannel` принимает положительный MAX-ответ
только если `recordBotAccessProbe` вернул true. Но `max-bot-link.service.ts:1066`
для отсутствующего membership или требуемой реактивации требует explicit activation
с доказательством администратора. Subscription-resolver такого доказательства
не передаёт; `allowMembershipRecovery=true` его не заменяет. Отказ сохранения
считается `stale`, и итоговая ошибка говорит, что бот должен быть администратором,
хотя MAX только что подтвердил обратное.

Воспроизведена цепочка с настоящим методом `recordBotAccessProbe`, искусственными
SQL-ответами «Chat существует / membership отсутствует» и MAX `isAdmin=true`:
итог HTTP 400. Это отдельная причина «бот админ, но канал не виден» для ещё
не активированного подключения. Для ранее подключённого исправного membership
этот сценарий не заявляется.

Разделить `probe_stale`, `activation_required`, `persistence_unavailable` и
реальную отрицательную роль. Показывать точное действие подключения/реактивации,
сохраняя найденный канал. Если текущий пользователь подтверждён администратором
самой цели, дать пройти существующий явный handshake; подтверждение прав в
исходной группе не выдаёт полномочий в чужом канале. Для партнёрского источника
нужно определить отдельное право чтения membership, не активирующее автоматически
модерацию/публикацию в цели. Не обходить explicit activation и retained ceilings
ради успешного выбора источника. Полный regression должен соединять resolver
и реальный persistence policy: мок `recordBotAccessProbe => true` скрывает проблему.

### A1 — каталог администраторов одновременно служит иммунитетом, P1

`moderation-access.service.ts:106` возвращает local admin до remote cache/lookup,
даже при `allowRemoteLookup=true`. `chat-context-cache.service.ts:2423` читает
roster без срока проверки. Финальные guards подписки/закрытия также учитывают
этот список. Воспроизведено: former-admin из local roster признан администратором,
remoteCalls=0 при подготовленном отрицательном remote-ответе.

Demand roster refresh в активных чатах существует, поэтому это **не утверждение**,
что запись никогда не удаляется. Но гарантированного срока переоценки именно
этого бывшего администратора на таком пути нет. После отказа от fleet refresh
каталог для навигации нельзя считать бессрочной авторизацией человека.

Разделить сохранённую связь user/chat, свежую роль человека и явный продуктовый
иммунитет. На сообщении участника проверять точного автора при необходимости,
с коротким положительным cache, batching и одним in-flight lookup; подтверждённая
демоция инвалидирует все реплики cache. На unknown — без санкции. Бессрочность
подтверждения **роли бота** при этом сохраняется. Не устранять проблему удалением
локальной защиты без замены свежим доказательством.

### P1 — правило пропуска просроченного поста, приоритет P1

`publication-late-policy.ts:4`, `publication-occurrence-dispatcher.ts:195` и путь
уже материализованных deliveries используют пятиминутное окно. Never-attempted
ONCE/SLOTS становятся FAILED, recurrence отменяет просроченный occurrence.
Отдельный explicit retry имеет собственный durable timestamp. Это защищает
от неожиданной публикации старого содержимого после восстановления доступа,
но теряет ожидаемую автоматическую доставку при долгом сбое.

Ввести явную политику опоздания в immutable revision публикации:

- Для новых заданий рекомендуемый режим — «отправить после восстановления»
  до заданного автором срока актуальности; пять минут сами по себе не закрывают
  никогда не начатую доставку.
- Доступен «строго до времени»: по истечении пост остаётся виден как просроченный
  с причиной, а не исчезает. Для существующих заданий сохранить прежнюю семантику
  до согласованной миграции; не оживлять старые FAILED/AMBIGUOUS автоматически.
- Для recurrence фиксировать каждое наступление и выбранную политику: догнать
  все в пределах срока либо только последнее. Рекомендуется последнее, чтобы
  восстановление не публиковало пачку устаревших постов. Пропуски видимы в истории.
- Разделять never-started, доказанный отказ до отправки, подтверждённую квитанцию
  и unknown outcome. Автоповтор разрешён первым двум. Начатый SEND без квитанции
  остаётся AMBIGUOUS; повтор возможен только через предусмотренный явный процесс.
- Для каждого occurrence/target всегда есть наблюдаемое состояние: ожидает,
  готовится, требуется действие, подтверждён, просрочен или исход неизвестен.

Это даёт отсутствие молчаливой потери задания. Гарантировать одновременно
безусловную доставку и отсутствие дублей при неизвестном результате MAX нельзя.

### P2 — общий координатор и недостаточный запас подготовки, приоритет P1

`publisher-background-work-coordinator.service.ts:77,96`: deadline ждёт завершения
активной lane. `publisher-chat-comment-recovery.service.ts` обрабатывает до 50
записей последовательно; auto-reply recovery — до 100; post-actions имеют мягкий
бюджет 10 с и remote timeout 10 с. Приоритет следующей lane не ограничивает
длительность уже начатой операции. Deadline runner имеет точный timer,
15-секундный safety poll и overdue rearm 250 мс — переписывать их с нуля не нужно.

`publisher-publication-access-preflight.service.ts:27` проверяет горизонт ±5 мин,
до двух целей одного occurrence за 2-секундный tick, до четырёх целей суммарно.
Для одного полностью неподготовленного occurrence верхняя граница — около одной
цели/с; 1 000 целей требуют не менее примерно 1 000 с номинации при отсутствии
других задержек. Это ограничение пропускной способности, а не замер production.
Задачи подготовки прав автора имеют отдельную очередь, но их номинация всё ещё
ждёт общего координатора. Права человека для отправки требуют freshness ≤15 мин.

Исправление без бесконтрольного роста параллелизма:

1. Изолировать due-send и nomination ближайших задач от длинных recovery sweep.
   У recovery — малые возобновляемые порции, cursor и yield между операциями.
   In-flight mutation не прерывать ради таймера; безопасно завершать её квитанцию.
2. Сохранить единый per-bot MAX limiter и durable SQL claim/fence. Дать ближайшим
   отправкам зарезервированный бюджет, а стареющей фоновой работе — ограниченную
   справедливую долю. Concurrency увеличивать только после измерения квоты и БД.
3. Подготавливать контент, media receipts и immutable targets заранее. Планировать
   actor proof по уникальным actor/bot/target и реальной доступной скорости,
   учитывать срок 15 мин, повторно использовать достаточно свежую проверку.
   Не возвращать ботам TTL и не проверять все 10 000 подключений.
4. Оставить SQL источником истины и один timer на ближайший срок; Redis wake —
   ускорение с периодическим восстановлением. После crash/restart потерянный wake
   не теряет occurrence, дубль wake не дублирует SEND.
5. Для большой одновременной рассылки рассчитывать достижимое время завершения:
   `число обязательных запросов / доступные запросы в секунду` плюс измеренная
   задержка MAX. Даже 1 000 SEND при полностью свободных 30 rps требуют ≥33,3 с.
   UI не должен обещать доставку во все цели в одну секунду.

### P3 — диагностика прав отстала от runtime, P1

`infra/scripts/publisher-publications-audit.mjs:175` по-прежнему выдаёт
`bot_access_expired` при null/старом `bot_access_expires_at`.
`publisher-readiness.service.ts:351` уже использует durable подтверждение роли
и capability. Следовательно, соответствующая причина в SQL-аудите не доказывает
реальную блокировку текущего runtime. В свежем отчёте такая причина встречается.

Согласовать audit с durable policy, явно отразить checkedAt/state/activation ceiling
и не выводить permissions payload. Добавить тесты паритета audit/runtime на
старом положительном proof, явном deny, unknown и будущей дате. Планы и grants
сохранить ограниченными. Не лечить «истёкшие права» массовым refresh по этому отчёту.

### P4 — одна неготовая цель удерживает подготовку всей публикации, P1

`publication.service.ts:2193` вызывает `prepareOccurrenceRoute` до транзакции,
создающей исполнения. `publication-publisher-routing.service.ts:240–266`
сначала требует готовности всех целей. В `publisher-readiness.service.ts:471–520`
одна отсутствующая/неготовая цель выбрасывает исключение из общего `map`.
`publisher-policy.service.ts:564–631` аналогично может отклонить разрешение всей
аудитории по одному участнику. Dispatcher откладывает occurrence целиком.
Приоритет готовых deliveries перед quarantine в recovery уже реализован, но
действует после материализации и эту раннюю блокировку не устраняет.

Изолированное воспроизведение через настоящие readiness и routing: 100 целей,
99 независимо проходят `canPublish`, в сотой бот — CONFIRMED_MEMBER. Общая
подготовка возвращает `bot_not_admin` до первого dialog context. Это доказанный
сценарий кода, а не установленная причина конкретного production-пропуска.

План: фиксировать аудиторию и состояние подготовки отдельно по каждой цели.
Готовые и авторизованные цели должны доходить до отправки независимо от
заблокированных. Причину отказа, retryAt/требуемое действие и исходный срок
оставлять у соответствующей цели; не удалять её и не объявлять весь пост успешно
доставленным при частичном результате. Общая ошибка контента или глобальная
недоступность runtime по-прежнему останавливает все затронутые цели.

Для snapshot сохранять immutable audience; для dynamic явно фиксировать момент
разрешения аудитории и её revision. Не расширять аудиторию при повторной подготовке
и не обходить actor proof, policy, bot identity или CAS ради частичного прогресса.
Подготовку dialog/media делать возобновляемой и идемпотентной по target/revision.
Приёмка: 100 целей/один явный deny; один unknown; доступ восстановлен после
частичной отправки; crash до/после materialization; изменение/отмена расписания
во время подготовки. Подтверждённые SEND не повторяются, блокеры остаются видимыми.

## Закрытие групп: целевое исправление и диагностика

Сначала различать четыре состояния: расписание включено; сейчас действует
ограничение; есть исполнимый маршрут удаления; уведомление доставлено/ожидает/неизвестно.
Уведомление требует `send_message`, удаление — отдельного права. Потеря только
отправки не должна выключать доступное удаление, и наоборот.

Контуры: `closed-chat-message-moderation.service.ts`, `closed-chat-delete-guard.service.ts`,
`night-mode-transition-scheduler.service.ts`, `night-mode-transition-reconcile.service.ts`,
`night-mode-transition-delivery.service.ts`, `night-mode-route-verification.service.ts`.

План N1, P1:

- В settings показывать фактический режим сейчас, timezone, ближайшее открытие,
  причину невозможности исполнять и отдельный статус последнего уведомления.
  «Закрыто» без доступного delete route должно сопровождаться состоянием проблемы.
- В текущий ограниченный audit добавить отдельные показатели due transition,
  durable intent, attempted SEND, remote receipt и фактического DELETE. Отдельно
  закрытые группы без подходящих membership/capability. Брать ограниченные
  индексные страницы; не возвращать fleet-проверки MAX.
- `catch_up_active` учитывать как ожидание, а не безымянную ошибку; сохранять
  начало ожидания и due. После бюджета ожидания проверять точный job/lock/ledger,
  с backoff и сигналом об отсутствии прогресса. Не сбрасывать lock/attempted marker.
- Явное восстановление подключения должно сразу номинировать reconcile конкретной
  группы. Не пытаться бесконечно отправить уведомление через известный запрещённый
  маршрут; другой подтверждённый исполнитель выбирается с теми же fences.
- После простоя восстанавливать только актуальный доказанный intent. Не отправлять
  исторические закрытия/открытия пачкой. Наличие события открытия в БД не подменяет
  квитанцию закрытия; отсутствие ledger не доказывает отсутствие попытки.
- Проверить расписания через полночь, timezone/DST, смену времени, force-close,
  открытие до исполнения DELETE, рестарт на границе, отсутствующий membership,
  разжалование автора, двух модераторов и медленный MAX. Равные начало/конец
  запрещены новым save; legacy-семантику проверять отдельно.

Удаление при закрытии имеет исходный пяти­минутный deadline и требует, чтобы
действовала та же сессия/настройки. Это защита от удаления старого сообщения
после открытия/повторного закрытия. Не расширять deadline ради сокрытия backlog;
сначала устранить задержку и обеспечить видимый результат отказа.

## Приоритеты реализации и критерии готовности

### Этап 1 — убрать потерю состояния и ложные причины

S1–S4 и P3; до изменения runtime сначала добавить воспроизводящие тесты.
Точечный canary на выбранных тестовых сущностях и fault-injection локально,
без публикаций в клиентские чаты. Приёмка: ноль удаления настроек по transient,
ноль bot-demotion по возрасту proof, поиск канала через другой модератор работает,
нет catalog/list MAX fanout при домашнем экране.

### Этап 2 — сроки Публика

Наблюдаемость + coordinator quanta + независимая подготовка due targets (P4),
затем явная late policy.
Не объединять изменение catch-up и параллельности в один непрозрачный выпуск.
Reuse существующих occurrence/delivery/ledger/fences; новые таблицы/очереди добавлять
только для недостающего durable состояния, с review индексов и совместимости rollback.

Метрики для каждого target: исходный scheduledAt, preparedAt, nominatedAt,
claimAt, sendStartedAt, MAX acknowledgement/remote receipt, verifiedAt,
retryAt, завершение и allowlisted причина. `claim lag` хранить отдельно.
`MAX accepted lag` и `verified visibility lag` — разные распределения: последнее
включает задержку проверки. Не терять confirmed-send timestamp из-за падения
постобработки pin/comments. Не использовать chat/user IDs как labels метрик.

Рекомендуемые **целевые**, ещё не достигнутые SLO при исправном MAX и нагрузке
в пределах квоты: p95 принятия одиночного запланированного поста ≤3 с,
p99 ≤10 с; минимум 99,9% таких отправок в пределах 30 с. Параллельно считать
безусловную долю всех scheduled targets, включая outages, access blockers,
expired/ambiguous: исключениями нельзя скрывать потери. Для массовой отправки
фиксировать достижимый диапазон завершения, первый/последний target и fairness.

Приёмка: 10 000 сохранённых чатов, 100/1 000 due targets, конкурирующие recovery,
429 с Retry-After, медленный MAX, 15 минут недоступности, потеря wake, restart
до/после remote receipt. Нет молча потерянных occurrence и повторного SEND после
неизвестного результата. Fresh author proof обеспечен именно к dispatch.

### Этап 3 — закрытие, роли автора и нагрузка модерации

N1 и A1. Для закрытия измерять webhook receive → durable delete intent → remote
DELETE confirmation и долю законно пропущенных сообщений по отдельным причинам.
Цель при штатной нагрузке: p95 подтверждённого удаления ≤2 с, p99 ≤5 с;
недоступность MAX и отсутствие прав отражаются отдельно. Эти числа — проектные
критерии, не результат этого аудита.

Общий backlog исследовать по закрытым receipt-когортам, per-stage admission,
ordered predecessor, retry и execution evidence. Сохранить независимый прогресс
чатов и uncertain-effect fences. Если снова возникает readiness 503, собирать
`queue`/`webhook-source-proof` **во время** отказа. Ошибка GET в антидублях должна
завершать конкретный безопасный отказ/ожидание; она не должна оставлять бесконечный
необъяснимый бизнес-claim. Перед исправлением доказать текущую стадию и квитанции.

### Этап 4 — остальные модули и эксплуатационные сигналы

Опросы: ограниченный backoff и reasoned terminal только при точном доказательстве.
Антидубли: разобрать fresh failed по конечным кодам, не выключать всё обнаружение
ради неизвестного GET. VK/suggestion/auto-reply: отдельные gauges возраста due,
cursor progress и terminal private recipient. OCR: причины отказа и quality
корпус отдельно от uptime sandbox. Retention: абсолютный срок и cleanup receipt.

Сигналы: ближайшая публикация не готова к due; overdue never-started без retryAt;
неопределённый SEND; due transition без intent; работающая closure без delete route;
растущий возраст ready DELETE; subscription target unknown дольше бюджета;
coordinator lane удерживается дольше порции. У каждого сигнала — конкретный
runbook, dedupe, owner и переход в recovery; периодический отчёт без изменения
состояния не должен засорять пользователя уведомлениями.

## Выпуск и откат

- Каждый этап — отдельный проверяемый commit. Старт с fault tests, затем
  соответствующие API/Redis/PostgreSQL проверки; UI/contract изменения добавляют
  проверки miniapp/admin/contracts и мобильные сценарии.
- Не менять runtime flags, customer settings или replay policy ради зелёной проверки.
  Production-тест SEND допустим только в явно назначенной тестовой цели.
- Runtime выпуск — штатный wrapper, зелёные Required и CodeQL точного SHA,
  все 14 API-ролей общего образа и необходимые static components. Postgres/Redis
  обычный выпуск не пересоздаёт; только затронутые компоненты.
- До выпуска — ограниченный baseline и rollback source, совместимый с durable
  access и существующими execution fences. Новая late policy должна оставаться
  читаемой rollback runtime; никакого отката на TTL/fleet-refresh реализацию.
- После выпуска — минимум 15 непрерывных минут с lag <10 с, точной fleet,
  доступными зависимостями и несколькими полными закрытыми когортами. Приёмка
  сроков публикаций требует реальных due cohorts, отдельно от общей readiness;
  затем 24 часа наблюдения, включая границы расписаний. Короткое ночное окно
  не подтверждает дневной пик и качество всех фильтров.

## Реализация и уточнения

S1–S4 сохраняют выбранные источники при временных ошибках, проверяют только добавления,
показывают сохранённые заголовки без MAX и ищут канал через ограниченный набор модераторов.
Уточнение S1: уведомление подписки обязательно для безопасной передачи DELETE; выключатель
не добавляется. Явный отказ доступа требует подключения через администратора, пассивный
успех не обходит этот барьер. Каталог и права бота остаются бессрочными до явного отзыва.

P2 выполнен независимыми ограниченными слотами deadline/preflight, а не прерыванием уже
идущих recovery-операций. Превышение пятисекундного бюджета даёт диагностический сигнал;
общий лимитер MAX сохраняется. P4 сохраняет всю snapshot-аудиторию, готовит ближайшие
получатели ограниченными страницами и проверяет каждого перед отправкой. Pending-контекст
не разрешает SEND даже на уровне SQL. Неизвестный SEND не повторяется.

Новые расписания получают явную latePolicy (по умолчанию 24 часа, последний повтор).
Старые без поля сохраняют пять минут; настройки сохраняются в локальном и серверном
черновике. Отменённые слоты учитываются в лимите новых повторов; materialization ограничена
300 слотами за проход. Время наблюдения ответа MAX измеряется отдельно от сохранения receipt;
это время возврата wrapper, не серверная метка MAX. Аудиты прав маркируются metadata_only.

A1 снимает вечный приоритет старого roster: точечный живой отрицательный ответ принимается
только под SQL fence относительно новых событий/подтверждений; при недоступном MAX остаётся
защитный fallback. N1 показывает ограничение, доступный DELETE-маршрут и receipt уведомления
отдельно, учитывает пересечение ручного/ночного закрытия и поколения восстановления.
Ожидание catch-up имеет ограниченное логирование. Опросы получают общий cooldown после
неопределённого read/edit, без ложного вывода о потере прав по общему 404.

Миграция `20261013090000_prepare_publication_targets_independently` добавляет проверку
pending-контекста и единственный переход в неизменяемый подготовленный контекст. Она не
переписывает данные и не сканирует историю; lock_timeout 5 секунд, statement_timeout 30 секунд.
Старые v1 строки удовлетворяют неизменённой ветке ограничения. Оба штатных отката требуют
новых reader/wiring: ранний образ нельзя считать допустимым только по совпадению схемы.

Полная регрессия и production-приёмка фиксируются после выполнения. Исторические количества
ошибок антидублей/OCR/kick сами по себе не доказывают новый дефект и не дают права на replay.
Целевые SLO и суточное наблюдение остаются отдельными критериями, а не обещанием по зелёному CI.

Диагностика закрытия загружается вместе с уже отложенным разделом ночного режима.
Новый ответ settings требует схемы closure в начальном пакете настроек: production-сборка
с Major API URL занимает около 145,5 КиБ gzip. Локальный JS-бюджет этого маршрута увеличен
с 148 608 до 149 120 байт (+512); startup, остальные маршруты и общий допуск не меняются.
Сценарий браузера ожидает видимый статус закрытия после открытия раздела.
Актуальные ограничения подготовки и трактовка бессрочных прав закреплены в
[диагностике публикаций](../runbooks/publisher-publication-diagnostics.md) и
[инструкции проверки доступа](../runbooks/publisher-access-refresh-rollout.md).

выполнил 21 367 тестов (851 набора прошли, в пяти оставались девять устаревших
ожиданий вызовов/лимитов/метрик). После исправления только этих ожиданий семь
связанных наборов, включая новый backoff опросов, прошли: 355 тестов без пропусков.
Нативные сценарии 100/1 000 получателей и возобновления после блокировки входили
в полный прогон. Проверки хранения: 50/50, miniapp: 1473/1473, Safety Desk: 21/21;
контракты: 407/407. Сборки API/Major/Safety Desk, Prisma, lint, guards и документация
прошли. Общий браузерный smoke и строгие iPhone/light, Android/dark для изменённых
экранов прошли. Полная проверка точного коммита и production-наблюдение остаются
следующим обязательным шагом; локальный первый staged-прогон сам по себе не зелёный.
