# Удаление голосовых по достоверному входящему событию

## Причина и поведение

MAX доставляет native `audio` через webhook, но может не возвращать это же
сообщение через GET. Обязательный повторный GET в нашей проверке блокировал
DELETE. Если `voiceMessagesEnabled=false` (голосовые запрещены), новое прямое
голосовое нужно удалять по точному ID из аутентифицированного события.

## План реализации

1. В одной транзакции с приёмом webhook сохранять компактное свидетельство:
   chat/message, автор, время источника, исходный срок и ID receipt. Нативные
   `audio`, `voice`, `audio_message`, `ptt` проверять по прямому вложению;
   имена файлов, MIME и вложенные цитаты не предоставляют это свидетельство.
2. Любое точное редактирование или удаление отзывает свидетельство уже на
   входе. Отзыв сохраняется и при доставке edit раньше create, зеркалах других
   ботов и неизвестном времени edit. Повторный create не восстанавливает отзыв.
3. Связывать новый `VOICE_BLOCKED_DELETE` с исходной политикой и пятиминутным
   сроком события. Перед DELETE проверять актуальный запрет, автора и его права,
   иммунитет, активного исполнителя, source holds и существующие SQL/lease fences.
   Повторно читать локальный отзыв после асинхронных проверок. Финальный SQL fence
   проверяет тот же абсолютный срок по часам БД. Ни очередь, ни рестарт его не продлевают.
4. Сохранить существующий durable intent и единственного исполнителя для зеркал
   нескольких ботов. Повторять только разрешённые временные сбои до исходного срока.
   Успехом считать подтверждённый DELETE, не пустой GET и не завершение webhook.
   Неизвестный результат мутации остаётся в существующем отдельном состоянии.
5. Добавить пустую таблицу с первичным ключом chat/message и индексом срока хранения.
   Обычные текстовые create не пишут в неё. Хранить записи/отзывы минимум сутки;
   удалять просроченное по индексу, не более 500 строк за существующий 30-секундный
   retention-проход, независимо от включения очистки тел webhook.
   Старые receipts и intents не переписывать. Оба API rollback сохраняют capture/
   invalidation reader, чтобы старый runtime не создавал пробел в учёте edits.
6. Проверить классификацию, отзыв, истечение, смену настроек, admin/immunity,
   несовпадение авторов/ID, отсутствие побочных санкций без DELETE, повторы и зеркала
   с настоящими PostgreSQL/Redis. Воспроизвести пустой MAX GET в полном webhook-пути.
7. Пройти impact checks и точный Required/CodeQL. Выпустить общий API-образ на все
   роли штатным deploy; проверить готовность, свежий поток и сохранность компонентов.
   Реальные test sends допустимы только в предусмотренных тестовых чатах.

## Границы

Новое свидетельство разрешает только удаление voice по собственному правилу.
Другие причины продолжают использовать их текущие проверки содержимого.
Оригинальное голосовое из жалобы старше пятиминутного срока: этот выпуск не
запускает его обработчик заново и не создаёт для него новую авторизацию.
Для источников без нового доказательства сохраняется прежний точный GET-путь.

Миграция `20261014030000_add_moderation_voice_sources` создаёт только новую
пустую таблицу и её индекс. Перестроения индексов исторических webhook, backfill,
расширения MAX квоты и повышения concurrency не требуется.

политики и rollback reader, 170 проверок классификации/guard/full-path на настоящих

пути с edit-before-delete также успешен; после корректировки ожиданий фоновой
очистки отдельно прошли все 175 проверок outbox. MAX в этих тестах моделируется,
поэтому это не доказательство удаления нового голосового в реальном чате.
