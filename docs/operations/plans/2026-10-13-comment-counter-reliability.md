# Заниженный счётчик комментариев — 13 октября 2026

Пользователь подтвердил симптом «число меньше реального». Ссылка на пост,
ожидаемое число и место отображения пока не предоставлены. Ниже разделены
воспроизводимый дефект и границы диагностики конкретной жалобы.

## Подтверждённый дефект ссылки счётчика

`PublisherChannelCommentDeliveryService` сохраняет существующую кнопку при
добавлении действий к посту. Однако прежний audit reference содержал заново
построенную кнопку. После смены ключа подписи старая ссылка может оставаться
валидной через validation keyring, но отличаться от вновь построенной.

При следующем комментарии число на кнопке не обновлялось: защищённый refresh ищет точную
установленную ссылку и возвращает no-op, если переданная ссылка отсутствует.
Комментарий виден в мини-приложении, а число под постом может оставаться старым.
Успешное завершение BullMQ job в этом случае не означает обновление счётчика.

Две новые регрессии воспроизвели ошибку до исправления: как при сохранении всей
клавиатуры без EDIT, так и при добавлении другого действия. В обоих случаях
refresh ошибочно вернул null. Исправление сохраняет фактически выбранные
Publisher-кнопки в reference. Подпись, URL, позиция и содержимое поста сохраняются;
Major-кнопка не становится источником счётчика Publisher. Тест дополнительно
проверяет валидность старой подписи текущим keyring и изменение только числа,
с сохранением фото, магазина и кнопки предложений.

Миграция, изменение contracts или static-компонентов не требуются. Runtime
исправление проходит стандартные API-проверки, exact-SHA CI и shared API deploy.
Исторические references этим изменением массово не переписываются.

## Что уже защищено существующим кодом

- Число читается из БД внутри общей возобновляемой блокировки редактирования
  сообщения; старый job не возвращает сохранённый `countSnapshot`.
- Повтор значения `1 → 2 → 1` не конфликтует с завершённой задачей очереди.
- Обновление меняет только существующую кнопку; удалённые ссылки и чужие
  обсуждения не восстанавливаются. MAX обязан подтвердить сохранение вложений.
- Мини-приложение загружает последние 80 комментариев с sentinel и показывает
  `80+` при наличии более старой истории. Это нижняя граница, не точное общее число.
- Нативные обсуждения MAX и комментарии мини-приложения — разные системы;
  их количества не складываются автоматически.

## Следующий шаг надёжности

Отдельный подтверждённый архитектурный пробел остаётся: comment commit и admission
обновления счётчика не образуют одну транзакцию. Ошибка после commit, потеря процесса,
отсутствующий reference или исчерпанные повторы могут оставить устаревшее число.
Для Major доставка остаётся best-effort; очередь Publisher закрывает только
часть этого окна. Исправление ссылки не выдаётся за transactional outbox.

Дальнейшая реализация должна сохранять dirty revision в той же транзакции,
что создание/удаление комментария, отдельно для profile/entity/chat/thread;
читать только due work через индекс, иметь bounded retry/backoff и CAS-завершение
точной revision. Смена revision во время EDIT оставляет новый пересчёт pending.
Нельзя восстанавливать счётчик повторной отправкой поста или ослаблением проверок
доступа, сохранности вложений и shared edit lock. Отдельно различать confirmed EDIT,
уже актуальное число, отсутствующую кнопку и недоставленное обновление.

Историческая починка требует точного списка постов: сначала readonly сравнение
ссылки и reference, затем адресная операция с актуальными правами и сохранением
исходной ссылки обсуждения. Массовый обход каналов или очистка очередей не нужны.
