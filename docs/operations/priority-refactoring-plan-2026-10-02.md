# MAXIM: приоритетный план рефакторинга, 2 октября 2026

План охватывает Publisher/Публик и общий тракт обработки событий всех настроенных ботов.
Основание — текущие исходники, сохранённые обезличенные измерения и официальная
документация MAX, повторно прочитанная 2 октября. Новый глубокий аудит ботов не проводился.

После подготовки плана пользователь поручил его реализовать с уточнениями по ходу работы.
Прежний мониторинг остановлен, автоматизация пока приостановлена; новое окно приёмки
будет относиться к проверенному выпуску исправлений. Сначала выполняется весь выбранный рефакторинг с
приёмкой, затем отдельная глубокая проверка всех ботов и исправление найденных ошибок.

### Прогресс реализации

- A реализован и объединён в PR #37: полная локальная проверка (14 868 API-тестов),
  PostgreSQL/Redis, сборка, Prisma и exact-SHA CI прошли. Runtime пока прежний.
- B реализован и объединён в PR #38; 14 892 API-теста и exact-SHA CI прошли. Воспроизведено ожидание реальной Redis-очереди за 100 подготовительными
  actor jobs; при двух workers и секундном времени это 50 секунд перед следующей публикацией.
  Добавлены ограниченный допуск, чередование occurrences, SQL-курсор аудитории и отдельная
  граница срочности. Новые сценарии 100/1 000 адресатов и гонки прав проходят локально.
- Уточнение B: не вводятся новый брокер, очередь или отдельные reason-идентификаторы.
  Совместимый job v1 сохраняет исходную причину, получает время наступления срочности;
  поздний admission не сбрасывает это время. Синтетический Redis-тест доказывает порядок
  и ограничение допуска; поддерживаемая реальная MAX-нагрузка требует production-приёмки.
- Уточнение A: публикационные deadlines jobs и срок старого bot proof имеют разную
  семантику. Обязательство идентифицируется SQL-снимком; ошибка диагностики делает покрытие
  неполным, но не отменяет committed grant. Retry не меняет знаменатель.
- C реализован: ограниченный admission по bot/work class, durable подготовка через существующий
  receipt/outbox и drain до закрытия SQL/Redis. Неопределённый обязательный owner probe
  остаётся на повторную проверку. См. [runbook](runbooks/webhook-preparation-bounds.md).
- D–E ещё не выполнены. Новый runtime не выпущен, 100% не включено.

## 3. A — достоверные доказательства и метрики

Основные файлы: [refresh coordinator](../../apps/api/src/publisher/publisher-binding-refresh.service.ts),
[bot executor](../../apps/api/src/publisher/publisher-bot-access-executor.ts),
[scheduler](../../apps/api/src/publisher/publisher-binding-refresh-scheduler.service.ts),
[queue](../../apps/api/src/publisher/publisher-binding-refresh.queue.ts),
[census](../../infra/scripts/publisher-access-census.mjs).

1. Возвращать из executor типизированное свидетельство: результат remote probe,
   время проверки, момент успешного сохранения, exact lifecycle/source version,
   срок старого доказательства. Сравнивать deadline с событием, делающим новый
   proof доступным для использования, а не с завершением catalog/roster стадий.
   Не удерживать SQL lock во время MAX/Redis-запросов.
2. Различать `confirmed_in_time`, `confirmed_late`, подтверждённый отказ,
   разрешённое точным чтением supersession, unresolved supersession и transient failure.
   Отказ MAX — корректный отзыв, а не успешное продление разрешения.
   Supersession подтверждается только свежим exact-bot SQL proof той же допустимой
   lifecycle generation; потерянный CAS сам по себе ничего не разрешает.
3. Разделить диагностику каждой попытки и SLA одного обязательства обновления.
   Retry не увеличивает знаменатель одного обязательства, поздняя повторная попытка
   не стирает исходный deadline. Явно учитывать обязательства, которым сканер ещё
   не создал job. При невозможности получить полный знаменатель — `insufficient_evidence`.
4. Публиковать ограниченные агрегаты: discovered/eligible/nominated/started/proof-committed,
   первые timestamps при продвижении, причины ожидания, scan cycles, visited/enqueued/deferred,
   compaction truncated/coverage и release boundary. Не хранить raw payload, токены,
   chat/user/bot IDs или job IDs в архиве измерений; внутренние точные ключи остаются
   в существующих рабочих структурах. Телеметрия не участвует в выдаче прав.
5. Считать roster отдельно для периодического maintenance и внеплановых manual/webhook
   операций. Формула сравнения: `1 - (periodic calls / comparable binding-hours)_separated /
(periodic calls / comparable binding-hours)_control`. Популяцию и допустимую погрешность
   определить заранее; не подменять её количеством выполненных jobs. При разных составах
   cohorts сравнивать сопоставимые группы, а не только общие суммы. Исторический контроль
   необходим для эффекта приоритетов: они уже включены у обеих текущих cohorts.

**Приёмка A:** настоящие PG-races для отзыва во время probe, новой generation,
CAS=0, commit после deadline и ошибки после успешного proof; Redis-retry без двойного
знаменателя; усечённые сканы и смена релиза делают отчёт неполным. Старые задания и
старые читатели метрик совместимы. Отчёт не превращает отсутствующие данные в нули.

## 4. B — Publisher: управляемый допуск вместо пачек

Основные файлы: [publication preflight](../../apps/api/src/publisher/publisher-publication-access-preflight.service.ts),
[readiness](../../apps/api/src/publisher/publisher-readiness.service.ts), scheduler и queue из A.

Сначала воспроизвести 100 одновременно устаревших actor-проверок, конкурирующие
публикации, ручную проверку и текущие bot-expiry/roster jobs. Разложить время на ожидание
допуска, очередь, лимитер MAX, remote probe и SQL. Проверить, какие стадии действительно
создают хвост; не выбирать новый batch size по одному production-снимку.

Ограничение мощности принципиально: для 100 разных jobs, двух свободных workers и
одинакового времени выполнения `s`, 95-я job начнёт примерно через `47 × s` даже
без фоновой нагрузки. При `s = 1 с` это около 47 секунд. Один приоритет не обеспечит
p95 ≤5 с. Это расчёт сценария, не измеренное среднее время MAX.

Предлагаемые изменения после воспроизведения:

- Выделить небольшой модуль admission policy: срочность, ближайший deadline,
  доступная мощность двух workers, уже принятые jobs, действующие bot/source budgets.
  Разделять заблаговременные проверки и действительно срочную работу, сохраняя
  earliest nomination при promotion и исходные delayed retry deadlines.
- Давать ручным операциям и наступающим публикациям ограниченный резерв обслуживания;
  распределять оставшийся бюджет между occurrences/actors и bot-expiry. Roster и
  обычные actor checks должны иметь измеримый прогресс при постоянной срочной нагрузке.
  Конкретные веса выбрать по тестам; не добавлять workers или очереди без необходимости.
- Порционно продвигать большую аудиторию с восстановимым прогрессом. Сначала проверить
  возможность восстановить курсор из имеющихся occurrence/target/version; новую SQL-модель
  вводить только если текущая не сохраняет нужный инвариант. Один большой occurrence
  не должен бесконечно удерживать preflight `pending` перед другими сроками.
- Не укорачивать выбранную аудиторию ради latency. Если прогнозируемая работа не помещается
  в срок при существующих лимитах, сохранять явное состояние задержки/блокировки и
  возможность штатного продолжения. Расширять lookahead только внутри бюджета свежести
  прав; ранняя проверка не разрешает отправку после истечения proof.
- Удалять повторную проверку bot/catalog из actor-пути только при доказанном избыточном
  вызове и точном свежем lifecycle-fenced proof. Результат случайного кэша или grant
  другого бота не подходит. Запрет на stale/denied send и TTL 15 минут сохраняются.
- Показывать время до enqueue отдельно. Перенос ожидания в admission не считается
  достижением SLA: суммарное ожидание от первой срочной nomination до start остаётся
  основной метрикой, а своевременный охват запланированных адресатов — отдельной.

**Приёмка B:** real Redis при concurrency=2 с пачками 100/1 000 адресатов,
постоянным фоновым потоком, несколькими авторами, 429/Retry-After и restart/queue-loss;
PG-races публикации с отменой, заменой автора, отзывом и новой revision. Зафиксировать
поддерживаемую нагрузку по фактическим stage times и лимитам MAX. В её пределах:
urgent p95 ≤5 с/p99 ≤15 с, достаточный прогресс maintenance и завершение проверок
до нужных deadlines. При перегрузке — ограниченная память, сохранённая работа и честный
overdue/blocked; не обещать эти же latency-пороги для произвольной нагрузки.

## 5. C — общий bounded webhook follow-up

Основные файлы: [WebhookService](../../apps/api/src/webhook/webhook.service.ts),
[ingestion facade](../../apps/api/src/webhook/webhook-ingestion.service.ts),
[outbox](../../apps/api/src/webhook/webhook-outbox.service.ts),
[worker shutdown](../../apps/api/src/runtime/runtime-worker-shutdown.ts).

Сохранить публичные фасады. Вынести из общего `deferBackgroundTask` только две
понятные границы: обязательные последствия принятого события и восстанавливаемые
проекции. Размер файла сам по себе не является основанием для переписывания.

- Membership transition, execution owner, отзыв доступа и подтверждение явного
  `Старт` не должны теряться при переполнении RAM или остановке процесса.
  Для каждой операции определить существующий receipt/intent, повторяемость и точку
  завершения. Где восстановления нет, добавить узкий durable handoff до отметки
  подготовки/завершения; предпочтительно использовать текущий outbox.
- Read-model refresh и наблюдательные записи обслуживать с общим потолком активных
  и ожидающих работ. Объединять только одинаковый exact key и совместимую версию,
  сохраняя более новое состояние. Не объединять независимые события ленты и
  переходы grant/revoke как обычное «последнее значение».
- Связать бюджет с пулом соответствующей роли; предусмотреть справедливость по bot
  и work class. Медленный MAX/DB одного потока не должен создавать неограниченное
  число ожидающих promises других ботов. Не вводить новый глобальный MAX rate limit.
- Существующие membership-denial tasks, publications и shutdown bounds сохранить.
  Новый контроллер не должен дублировать их или ждать сам себя. Завершение процесса
  прекращает приём, ограниченно дренирует работу и оставляет durable остаток для recovery.
- На пути ACK оставить аутентификацию и durable receipt. Рефакторинг read models
  не должен откладывать обязательные security transitions либо подтверждать событие,
  которое сохранилось только в памяти. Публиковать in-flight/pending/coalesced/deferred,
  pool wait и восстановление, с фиксированными метками без пользовательских данных.

**Приёмка C:** bounded burst-тесты на общей цепочке нескольких ботов, уникальных и
повторных keys; отзыв/повторное добавление, mirrored event, ошибка БД/Redis и SIGTERM
на каждой границе durable handoff. Число in-flight/pending не превышает заданных
лимитов; важная работа либо выполнена, либо восстановима; ACK укладывается в текущий
внутренний deadline. Никаких новых диагностических сообщений в пользовательских чатах.

## 6. D — условный пакет справедливости outbox

Начать с существующих [PostgreSQL outbox tests](../../apps/api/src/webhook/webhook-outbox-postgres.spec.ts).
Создать горячий чат с >1 000 событий в degraded и >5 000 в normal, независимый чат
в середине хронологии, непрерывный новый хвост, due retries и retained quarantine.
Проверить продвижение каждого eligible work unit за ограниченное число проходов.

Если текущий oldest/newest отбор систематически не видит независимое событие,
выделить policy отбора и добавить ограниченный keyset-проход среднего backlog с
фиксированным горизонтом и wrap-around. Сохранить exact ordered head перед CAS,
per-chat порядок, semantic dedupe, резервы старых/новых receipts и паузы recovery.
Не увеличивать overscan, не применять OFFSET/глобальный JSON-scan и не переносить
живую работу между шардами без существующего routing fence.

**Приёмка D:** реальный PG подтверждает дефект до изменения и прогресс после него;
EXPLAIN и число прочитанных строк укладываются в фиксированный бюджет, путь restore
курсора не теряет строки, новый хвост не мешает обходу старого. Если сценарий проходит
на текущем коде, сохранить полезную регрессию и закрыть пакет без изменения production SQL.

## 7. E — завершение рефакторинга и выпуск

1. Для каждого PR — impact plan, публичные locked проверки затронутых областей,
   `check:api`, guards и реальные PG/Redis сценарии там, где меняются гонки/очереди.
   Новая схема требует forward-only migration и `check:prisma`; contracts требуют
   проверок API, mini app и admin. Исторические миграции неизменны.
2. Перед выпуском — зелёные `Required` и `Analyze JavaScript and TypeScript` для
   точного SHA, migration/reader compatibility и rollback floor. Общий API-образ
   разворачивается штатным queue-fenced rollout во всех 14 ролях. При изменении
   Compose следовать classifier: он может выбрать также оба static-компонента.
   Не пересоздавать PostgreSQL/Redis и не снижать disk floor.
3. Возврат к наблюдению — только в рамках возобновлённого пользователем этапа внедрения,
   с новым ограниченным окном и явными start/end/release. Автоматизация, остановленная
   2 октября, не запускается этим планом. Старые 3 часа не превращаются в сутки после
   ожидания по календарю и не склеиваются с другим runtime как однородная выборка.
4. После A/B провести минимум 24 часа сопоставимой canary-приёмки по обновлённому
   [runbook](runbooks/publisher-access-refresh-rollout.md): urgent p95 ≤5 с/p99 ≤15 с;
   ≥99,9% своевременных подтверждений bot-access по полному знаменателю; ≥50% сокращения
   периодических roster calls на сопоставимую binding/time exposure; завершённые
   scan cycles, достаточная выборка и отсутствие регрессий отправки/доступа/модерации.
   Метод знаменателя, обработку подтверждённого отзыва и достаточность выборки
   фиксировать до начала: не исключать ошибки и неудобные случаи после измерения.
5. Дополнительно проверить общую цепочку событий нескольких ботов: максимальный
   in-flight/pending, продвижение oldest eligible, p95 подготовки, ошибки pool/Redis/MAX
   и восстановление. Сравнивать одинаковую нагрузку и классы работ; `health=200`,
   текущая свежесть proof и завершённый job по отдельности недостаточны.
6. Только при выполненных gates выпустить проверяемое включение `on` во всех ролях,
   подтвердить image/config identity и штатные smokes. Проверка после переключения
   должна включать queue-loss recovery и фактическую работу полного roster scheduler,
   а не лишь значение environment. Если управление режимом не позволяет такой
   проверяемый rollout, сделать отдельное узкое изменение tooling.

Rollback каждого пакета сохраняет SQL evidence, intent/job identity и delayed deadlines.
Для регрессии Publisher вернуть явный `off` штатным совместимым rollout либо известный
совместимый release. Off не отменяет уже отправленное сообщение. Не повторять ambiguous
send, не очищать очереди и не удалять ledger для восстановления зелёного dashboard.

## 8. Границы приоритета и следующий этап

В этот цикл не включаются: смена брокера/framework, новые микросервисы, общий workflow
engine, переписывание OCR, расширение native comments, косметическая декомпозиция всех
legacy-файлов, рост concurrency/SQL pool без измерений и очистка истории сообщений.
Уже выполненные storage/write/cache/image оптимизации не обещаются как новый выигрыш.
Исторический retention и физическое освобождение БД остаются отдельной работой с
проверенным backup/restore и [своими gates](runbooks/storage-cost-rollout.md).

После полного завершения E начинается отдельный глубокий аудит **всех реально
настроенных ботов**, включая Publik: registry/lifecycle/identity, webhook/subscriptions,
ownership/failover, доступ, модерация, публикации, частные диалоги и восстановление.
Количество API-ролей не равно количеству ботов; census Publisher с одним bot scope
не подтверждает работу остальных. Список берётся из актуальной конфигурации без
экспорта токенов. Подтверждённые дефекты исправляются отдельными проверяемыми PR.
Живые мутации допускаются только в тестовых сущностях из API AGENTS и при здоровом
production; пользовательские чаты не используются для диагностики.

## 9. Проверенные внешние основания

Официальные страницы MAX прочитаны 2 октября 2026; production MAX-вызовы для этого
плана не выполнялись. Перед изменением соответствующего контракта проверить их снова.

- [API overview](https://dev.max.ru/docs-api) и [changelog](https://dev.max.ru/docs-api/changelog-api):
  `platform-api2.max.ru`, Authorization header, снятие `GET /chats`; discovery остаётся
  событийным. Overview также сообщает удаление добавления участников через
  `POST /chats/{chatId}/members` с 30 сентября. Существующее отключение UNBAN не отменять.
- [Webhook subscriptions](https://dev.max.ru/docs-api/methods/POST/subscriptions):
  HTTP 200 в течение 30 секунд, до 10 повторных попыток, автоматическая отписка при
  отсутствии успешного ответа 8 часов. Поэтому ACK и durable receipt остаются
  обязательной границей общего рефакторинга.
- [Получение участников](https://dev.max.ru/docs-api/methods/GET/chats/-chatId-/members):
  targeted `user_ids` поддерживается; при его указании `count`/`marker` игнорируются.
  Не заменять точечную проверку нужного пользователя полным admin roster.

Готовность этого плана означает конкретный объём A–C, проверку условия D и gates E.
Она не означает, что рефакторинг уже принят, все боты проверены или canary разрешено
автоматически расширять.
